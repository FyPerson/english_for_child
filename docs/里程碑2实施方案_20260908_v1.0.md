## 1. 为什么现在做

## 3. 设计决策

### 3.1 三层概念：字位 ID / 字形 / 表面串

首审 C-1 的根因是 v0.1 只想着"把字符串换成数组"，没区分这三层。定义如下，本方案后文一律按此用词：

| 层 | 是什么 | 例 | 用在哪 |
|---|---|---|---|
| **字位 ID** | `SOUNDS` 的键，稳定标识 | `'r'`、`'ai'`、将来的 `'oo_short'` | 槽位、比较、rack、四个字段 |
| **字形 `grapheme`** | `SOUNDS[id].grapheme`，它实际的字符串 | `'r'`、`'ai'`、`'oo'` | 一切显示：tile 文字、ARIA、CSS 类 |
| **表面串** | 词本身，等于各字位字形依次拼接 | `'rain'` | 查词：`W` 的键、G5 白名单、`confirms` 键、音频键 |

**硬规则**：

- 凡是"有几块""摆对没有"——用 **ID 数组**，逐项比较，不用 `join('')`。
- 凡是给人看的——用 **grapheme**，不要把 ID 直接渲染出去。单字母字位两者相同，所以现在看不出差别；`oo_short` 一旦出现，直接泄漏到孩子界面。
- 凡是查表——用 **表面串**，由 `surfaceOf(ids, SOUNDS)` 生成，不靠 `slots.join('')` 偶然成立。

G4 因此改成：先取目标词的字位序列 `targetIds`，槽数用 `targetIds.length`，判定逐项比较 ID；G5 的 `slots` 存 ID，查词前先过 `surfaceOf`。

**文案同步改**：`games.js:390` 的「听到的词是 N 个字母」改成「N 块积木」。课程方案 §5.3 的说法就是"两个字母一块积木"，说"字母"会和教学口径打架。

### 3.2 `segmentWord` 契约

v0.1 的 `tokenize(word, patterns)` 只有签名没有语义，`patterns` 到底是 ID 数组、字形数组还是映射也没定义（首审 H-3）。改为：

```js
segmentWord(word, sounds, explicitSegments?) -> string[]   // 字位 ID 数组
```

契约逐条写死：

- **匹配依据固定为 `SOUNDS[id].grapheme`**，不是键本身——`oo_short` 这个键不会出现在任何单词里。
- **规范化**：先 `toLowerCase()`（`check_data.js:133` 现在就是这么做的），规范化后的串用于匹配。
- **最长匹配优先**。
- **同长度多解 → 抛歧义错误**，绝不按对象键顺序任选一个（规范 §3 原文要求）。
- **未知区间 → 抛未知错误**。
- **空串 → 抛错**。
- 传了 `explicitSegments` 时：校验 `surfaceOf(explicitSegments) === 规范化后的 word`，不一致抛错；一致则原样返回，不再自动匹配。
- **错误是结构化对象**，带 `{word, offset, candidates}`，让校验器能指出是哪个词的哪个位置需要消歧。
- **确定性**：同输入同输出，不依赖 `SOUNDS` 的键枚举顺序。

配套导出：

```js
surfaceOf(ids, sounds)            // 字位 ID 数组 → 表面串
graphemeLabel(id, sounds)         // 字位 ID → 显示字形
soundType(id, sounds)             // 字位 ID → 'c' | 'v'
normalizeIdList(value)            // 迁移期双读，见 §3.5
colorTokenizedText(text, sounds)  // 分隔符感知着色，见 §3.3
```

底层可以另有一个收预编译索引的纯函数做性能优化，但**对外只暴露上面这组**，不暴露含义不明的 `patterns`。

`sounds` 参数必须传**追加键之后**的 `SOUNDS`（§2.4 的 `k`）。

### 3.3 句子与正文的着色

`colorWord` 有 42 个调用点，其中三处传的是含空格标点的整句（书名、书页正文）。对整串做严格分词必然抛错。

新增 `colorTokenizedText(text, sounds)`：**先保留分隔符地切词，再逐词尝试分词**——能分的按字位着色，不能分的（专有名词、标点、数字）原样输出，不抛错。单词场景仍走严格路径，分不出来就是数据错误，应该报。

这是"降级要换形态"的应用：句子里遇到不认识的词，换的是渲染方式（原样输出），不是删掉着色能力。

### 3.4 同形多音：本次冻结接口并实现检测

v0.1 说"现在只在 `SOUNDS` 键上留出空间，不写消歧逻辑"，理由是"没有数据可验"。首审 H-6 判这个理由不成立，**用户已拍板纳入**：

- 规范 §3 已经规定了行为（多解且无 `segments` 即失败），这条**现在就能用合成 `SOUNDS` 验证**，不必等 W13 的生产数据。
- 不冻结返回与错误契约，W13 前要改公共 API、全部调用方和缓存结果——那就是第二次破坏性变更，正是本次想避免的。

所以本次做：歧义**检测**、显式 `segments` 的**消费接口**、合成 fixture（`oo_short` / `oo_long`）。生产周的 `W[词].segments` 可以暂不填写——未来只增加数据，不改调用接口。

### 3.5 双读兼容层（用户拍板）

v0.1 说第 3 步"不可分割、没有中间态"。首审 H-7 判这不是技术必然，是没区分**仓库提交原子性**与**运行时 schema 原子性**。**用户拍板采纳双读**：

```js
normalizeIdList(value)   // 字符串 → 按旧单字符 schema 展开；数组 → 按 ID 原样保留
```

关键不在"能逐周迁移"——四周数据同构，逐周迁移发现不了新问题；关键在**让含 `ai` 的集成 fixture 在破坏性迁移之前就跑通全链路**（首审 H-8）。v0.1 把双字母冒烟排在第 5 步，意味着最关键的新能力直到破坏性迁移完成后才第一次被验证。

**存续期写死**：第 1 步引入，第 6 步删除字符串分支并加"拒绝旧格式"失败测试。不留到里程碑 2 之外。

反解析侧同样要能区分新旧格式，不能把字符串 `"ai"` 错当成两个 ID。

### 3.6 分组固定位与 tile class

`groupedRackHTML`（`games.js:583`）用 `vowels.includes(ch)` 判元音，改字位后 `vowels.includes('ai')` 必然失配。改用 `soundType(id) === 'v'`——`type` 字段 schema 里本来就有，四周实测齐全（W4 = 14 辅音 + 5 元音）。

首审 M-9 指出两件 v0.1 漏的：

- **不止 `groupedRackHTML`**：四个模板各有 1 处 `vowels.includes(c)`，G4/G5 自己的 tile class 也在用，必须一起换成 `soundType`。
- **分类正确不等于固定位不变**：固定位还依赖 rack 数组顺序、重复项顺序和 CSS 布局。要加断言——分组前后每个 tile 的**原始 rack 索引、重复项数量、组内顺序**都不变，并覆盖 `ai` 作为元音的案例。

### 3.7 三个字段的数组形态

```js
wallLetters: ['s','a','t','i','p','n']                       // 有序，等于 SOUNDS 全部键（§2.4）
rackG4: ['s','s','a','a','t','t','i','i','p','p','n','n']    // 保留重复，长度即块数
rackG5: [...]                                                 // 同上
newPatterns: ['ai','j']                                       // 本周新点亮
```

**保留重复是硬要求**（§2.3）。`canSpell` 的逐个消耗语义不变，只是消耗单位从字符变成字位 ID。

## 6. 风险

- **week04 余量 0.38 MB**。首审 M-10 判 v0.1 的"不加媒体所以不会触线"证据不足：单文件构建会把公共 JS 复制进每个产物，新增解析器、错误文本和兼容分支都会进去，方案自己也承认 data.js 会增大。改为**低风险但必须测量**，每个接线提交记录增量。
- **墙语义统一改变已交付课件的呈现**（§2.4）。W2、W3 的家长和孩子会看到墙上块数变多。这是规范要的效果，但属于可见变化，第 5 步后要实际打开页面确认排版没被撑坏。
- **第 5 步仍是大 commit**，回滚范围是整个 commit。做之前先 `git rev-parse HEAD` 记基线。
- **兼容层是临时代码**。第 6 步必须删干净，否则字符串分支会变成长期技术债，也让"四个字段是 ID 数组"这条契约失去强制力。
- **审查轮次不可控**。2026-09-08 三份文档分别走了五、六、五轮；代码改动的审通常更细。首审已出 2 critical + 6 high，后续每步接线都要送审。
