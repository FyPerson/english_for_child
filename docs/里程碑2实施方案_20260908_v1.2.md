### 0.3 `DATA-ASSESS-01` 为什么不能整体拆出

v1.0 把它整体拆到里程碑 2b，复审 C-1 判为**阻断性矛盾**，本地核实成立：

- `assessment_contract.js:5` 是 `if(d.META.week < 4) return []`——**W5 会进入完整校验**，`:7` 要求 `RESERVED`、`RESERVED_RETEST`、`PROBE_A`、`PROBE_B`、`GLOBAL_RESERVED` 五个池齐全，`:10` 要求 `RESERVED` 与 `RESERVED_RETEST` 各 5 词，`:13` 要求 `GLOBAL_RESERVED` 完整保留附录 B 的 40 词。

所以整体拆出的结果是：W5 要么塞进一堆无意义常量才能过校验，要么根本装配不了。**基础假设「拆出后不阻塞 W5 装配」不成立。**

**改为两段切分**：

|---|---|---|
| **最小路由** | **里程碑 2** | `META` 新增 `assessmentMode` 字段；`validateAssessment` 的门槛从 `week < 4` 改为按 `assessmentMode` 路由；weekly 周只要求 `RESERVED`。**这是 W5 能装配的前提** |

### 2.4 墙语义统一的实际后果

规范 §3 定义 `wallLetters` 是「墙上**完整**的积木集合，有序」，等于 `SOUNDS` 全部键；本周新点亮的由 `newPatterns` 表达。现状按周型跳变。统一后：

| 周 | `SOUNDS` 键数 | `wallLetters` 现值 | 统一后 | 后果 |
|---|---|---|---|---|
| W1 | 6 | 6（`satipn`） | 6 | 不变 |
| W2 | **13**（12 + 追加的 `k`） | **7**（`ckehrmd`） | **13** | **墙 7 块 → 13 块** |
| W3 | **19**（18 + 追加的 `k`） | **6**（`goulfb`） | **19** | **墙 6 块 → 19 块** |
| W4 | 19 | 19 | 19 | 不变 |

**这是已交付课件的呈现改变，不只是类型迁移。** 第二、三周的孩子会看到墙上多出此前学过的积木（未点亮态），这正是规范想要的"墙是完整集合、新的靠动画区分"。

两件事必须同时做，否则改了等于没改：W2/W3 的模板是**硬编码字面量**，不读 `META.wallLetters`——只改 data.js，页面还是显示旧的 7 / 6 块。

`k` 是**追加键**（`week02.data.js:106`、`week03.data.js:150` 的 `SOUNDS.k = Object.assign({}, SOUNDS.c, { L:'k' })`，c/k 同音共享录音但是两块积木）。分词函数取字位表必须在追加之后，否则 `k` 不在表里。反解析侧已经支持——`load_data.js:17` 有 `raw.match(/^SOUNDS\.\w+ = Object\.assign\(.*?\);$/gm)` 专门收这类追加声明。

**墙的顺序需要独立真相源**（三审 H-3）。规范既要求 `wallLetters` 顺序有教学意义，又明确说不依赖对象键枚举顺序——那么校验时的"期望顺序"不能取 `Object.keys(SOUNDS)`（违反后一句），也不能取 `wallLetters` 自己（循环校验）。

**真相源定义为：按 `project.json` 的周序，依次累计各周 `newPatterns`，同周内按 `newPatterns` 自身顺序追加。** 别名类追加键（`k` 这种由 `Object.assign` 派生的）紧跟其本体之后。`DATA-WALL-01` 拿 `wallLetters` 与这个独立序列比，而不是与 `Object.keys(SOUNDS)` 比。

### 2.5 基线比对四项

fixture 里记四项：`sha256`、`skeletonSha256`、`declarationOrder`、`media`。但**自动门槛只有后三项**——`baseline.py:210-224` 的 `differences()` 只比较 `skeletonSha256`、`declarationOrder` 与 `media`，**不比较周 `sha256`，也不比较 `course.sha256`**（三审 H-4）。

所以口径写清楚：**`sha256` 是审计元数据，不是自动门槛**。改 `META` 会改变 data.js 内容进而改变产物，`sha256` 与 `skeletonSha256` 都会变，但校验器只会因 `skeletonSha256` 变化而报错。基线仍必须在改造完成后重取，验收按工具真正检查的三项写（§5）。

首审 M-11 补充：`baseline --create` 会先构建并要求构建**不产生 tracked 变更**，所以重取之前必须已提交全部受版本控制的派生物，工作树干净——否则该命令直接拒绝。

## 3. 设计决策

### 3.1 三层概念：字位 ID / 字形 / 表面串

首审 C-1 的根因是 v0.1 只想着"把字符串换成数组"，没区分这三层。定义如下，本方案后文一律按此用词：

| 层 | 是什么 | 例 | 用在哪 |
|---|---|---|---|
| **字位 ID** | `SOUNDS` 的键，稳定标识 | `'r'`、`'ai'`、将来的 `'oo_short'` | 槽位、比较、rack、四个字段 |
| **字形 `grapheme`** | `SOUNDS[id].grapheme`，它实际的字符串 | `'r'`、`'ai'`、`'oo'` | 一切显示：tile 文字、ARIA、CSS 类 |
| **表面串** | 词本身，等于各字位字形依次拼接 | `'rain'` | 查词：`W` 的键、G5 白名单、`confirms` 键、音频键 |

**硬规则**：

- 凡是"有几块""摆对没有"——用 **ID 数组**，逐项比较，不用 `join('')`。
- 凡是给人看的——用 **grapheme**，不要把 ID 直接渲染出去。单字母字位两者相同，所以现在看不出差别；`oo_short` 一旦出现，直接泄漏到孩子界面。
- 凡是查表——用 **表面串**，由 `surfaceOf(ids, SOUNDS)` 生成，不靠 `slots.join('')` 偶然成立。

**第四条：机器身份与外部键**（复审 M-10）。上面三层覆盖的是数据转换，但还有一类消费是"拿什么当标识符"：

- **确认状态、槽位、DOM `data-*`、业务比较** → 用稳定 **ID**。同形多音若用 grapheme 当键，`oo_short` 和 `oo_long` 会共享确认状态。
- **词级持久状态** → 用规范化**表面串**。
- **音频** → 必须经 `audioKey` 解析，不能拿 ID 或 grapheme 直接拼文件名（`k` 与 `c` 共享录音正是靠它）。
- **CSS 类名** → 不得直接拼接未经转义的 ID；`oo_short` 这类带下划线的还好，将来若有特殊字符会产生非法或难选择的选择器。

这四类已列进 §2.2 迁移矩阵。

G4 因此改成：先取目标词的字位序列 `targetIds`，槽数用 `targetIds.length`，判定逐项比较 ID；G5 的 `slots` 存 ID，查词前先过 `surfaceOf`。

**文案同步改**：`games.js:390` 的「听到的词是 N 个字母」改成「N 块积木」。课程方案 §5.3 的说法就是"两个字母一块积木"，说"字母"会和教学口径打架。

### 3.2 `segmentWord` 契约

v0.1 的 `tokenize(word, patterns)` 只有签名没有语义，`patterns` 到底是 ID 数组、字形数组还是映射也没定义（首审 H-3）。改为：

```js
segmentWord(word, sounds, explicitSegments?) -> string[]   // 字位 ID 数组
```

契约逐条写死：

- **匹配依据固定为 `SOUNDS[id].grapheme`**，不是键本身——`oo_short` 这个键不会出现在任何单词里。
- **规范化**：先 `toLowerCase()`（`check_data.js:133` 现在就是这么做的），规范化后的串用于匹配。
- **歧义按「整词有几种完整分词」判，不是按「当前位置有几个同长度候选」**。复审 H-3 指出 v1.0 的「最长匹配优先 + 同长度多解抛错」只能抓局部冲突：若字位表含 `a`、`ab`、`bc`、`c`，则 `abc` 有 `ab`+`c` 与 `a`+`bc` 两种完整解，**首段长度不同**，局部规则一个都抓不到。规范 §3 要的是「出现多解即失败」。
  所以契约是：**求整词的全部可行分词——0 解报未知，恰好 1 解返回，多于 1 解报歧义**。最长匹配只能用作剪枝或在已证明全局唯一后的选择依据，不能用来消灭合法的较短起始路径。
- **复杂度有界**（复审 M-12）：用按 offset 记忆化的动态规划或 trie，状态只保留「0 解 / 唯一解 / 多解」三态加有限几个候选用于报错，**不枚举全部解**，避免前缀高度重叠时的指数回溯。
- **未知区间 → 抛未知错误**。**空串 → 抛错**。
- **`explicitSegments` 的完整校验**（复审 H-5）：必须是非空字符串数组；每个元素必须是 `sounds` 的**自有键**；`surfaceOf(explicitSegments)` 必须等于规范化后的 word。任一条不满足即抛结构化错误。`displayOnWall:false` 只影响墙展示，**不影响分词资格**。
- **`surfaceOf`、`graphemeLabel`、`soundType` 遇到未知 ID 一律抛同一种结构化错误**，不返回 `undefined` 让它在下游变成难定位的异常。
- **错误是结构化对象**，带 `{word, offset, candidates}`，让校验器能指出是哪个词的哪个位置需要消歧。浏览器构建可只带精简错误码，Node 校验器补详细位置说明。
- **输入 schema 先验**（三审 M-7）。建索引前先校验，不合法立即抛：`word` 必须是字符串；`sounds` 必须是普通映射且**只读自有键**（不走原型链）；每项的 `grapheme` 必须是非空字符串，且规范化后仍非空。**空 grapheme 必须在进 DP 前失败**——否则会产生零长度转移，DP 状态图出现自环而不前进。
- **`offset` 的口径**：以**规范化后**的串计，用 UTF-16 索引，浏览器与 Node 必须一致。
- **确定性**：同输入同输出，不依赖 `SOUNDS` 的键枚举顺序。

配套导出：

```js
surfaceOf(ids, sounds)            // 字位 ID 数组 → 表面串
graphemeLabel(id, sounds)         // 字位 ID → 显示字形
soundType(id, sounds)             // 字位 ID → 'c' | 'v'
normalizeIdList(value)            // 迁移期双读，见 §3.5
colorStrictWord(word, sounds)     // 单词：分不出就是数据错误，抛
colorPlainText(text, sounds)      // 纯文本句子：逐段转义，未知词降级
colorRichText(html, sounds)       // 受限富文本：白名单解析后只着色文本节点
```

底层可以另有一个收预编译索引的纯函数做性能优化，但**对外只暴露上面这组**，不暴露含义不明的 `patterns`。

`sounds` 参数必须传**追加键之后**的 `SOUNDS`（§2.4 的 `k`）。

### 3.3 句子与正文的着色

`colorWord` 有 42 个调用点，其中三处传的是含空格标点的整句（书名、书页正文）。对整串做严格分词必然抛错。

结果会进 `innerHTML`，所以**按输入是不是富文本拆成两个接口**（复审 H-6）：

| 接口 | 输入 | 规则 |
|---|---|---|
| `colorStrictWord(word, sounds)` | 单个词（词卡、tile、G2 积木态） | 走严格分词，分不出来就是数据错误，**抛结构化错误** |
| `colorPlainText(text, sounds)` | 纯文本句子（书名、书页正文） | 先保留分隔符地切词，逐词尝试分词；能分的着色，不能分的降级为原样；**每一段非着色文本必须 HTML 转义**后再拼回 |
| `colorRichText(html, sounds)` | 允许标记的字段 | 按白名单解析后**只对文本节点着色**，标签结构保留 |

**白名单是完整结构，不只是标签名**（三审 M-8）：`<b>` 无属性、`<br>` 无属性、`<span>` 仅允许 `class` 且值严格等于 `en`。**其余标签与任何其他属性一律拒绝，不是保留**——只限制标签名挡不住 `span` 上的事件属性、`style` 或危险实体。实现优先用 `DOMParser` 建节点再重新序列化；Node 侧用同一实现或至少同一组测试向量。

**42 个调用点必须逐项登记归类**（三审 H-2 / RECOMMENDATIONS）：不能只凭"有两个接口"就声称覆盖。落地时产出一份调用点清单，每项标注走 strict / plain / rich 哪一条，作为第 4 步的交付物之一。

**禁止用正则直接在整段 HTML 上分词**。单词场景仍走严格路径，分不出来就是数据错误，应该报。

四周现有数据的 `line` / `title` 实测**都不含标签**，但 `assessment_contract.js:2` 的 `tokens()` 里有 `replace(/<[^>]*>/g, ' ')`——系统是**预期文本可能带标签**的，所以边界必须现在定义，不能靠"当前数据碰巧没有"。要加尖括号、`&`、引号和允许标签的 fixture。

不能分的词原样输出（转义后），是"降级要换形态"的应用：句子里遇到不认识的词，换的是渲染方式，不是删掉着色能力。

### 3.4 同形多音：本次冻结接口并实现检测

v0.1 说"现在只在 `SOUNDS` 键上留出空间，不写消歧逻辑"，理由是"没有数据可验"。首审 H-6 判这个理由不成立，**用户已拍板纳入**：

所以本次做：歧义**检测**、显式 `segments` 的**消费接口**、合成 fixture（`oo_short` / `oo_long`）。生产周的 `W[词].segments` 可以暂不填写——未来只增加数据，不改调用接口。

### 3.5 双读兼容层（用户拍板）

v0.1 说数据迁移那一步（它的第 3 步，编号与本版无关）"不可分割、没有中间态"。首审 H-7 判这不是技术必然，是没区分**仓库提交原子性**与**运行时 schema 原子性**。**用户拍板采纳双读**：


关键不在"能逐周迁移"——四周数据同构，逐周迁移发现不了新问题；关键在**让含 `ai` 的集成 fixture 在破坏性迁移之前就跑通全链路**（首审 H-8）。v0.1 把双字母冒烟排在最后一步，意味着最关键的新能力直到破坏性迁移完成后才第一次被验证。

### 3.6 分组固定位与 tile class

## 6. 风险

- **week04 余量 0.38 MB**。首审 M-10 判 v0.1 的"不加媒体所以不会触线"证据不足：单文件构建会把公共 JS 复制进每个产物，新增解析器、错误文本和兼容分支都会进去，方案自己也承认 data.js 会增大。改为**低风险但必须测量**，每个接线提交记录增量。
- **墙语义统一改变已交付课件的呈现**（§2.4）。W2、W3 的家长和孩子会看到墙上块数变多。这是规范要的效果，但属于可见变化，第 7 步后要实际打开页面确认排版没被撑坏。
- **第 7 步仍是大 commit**，回滚范围是整个 commit。做之前先 `git rev-parse HEAD` 记基线。
- **兼容层是临时代码**。第 8 步必须收紧干净，否则字符串分支会变成长期技术债，也让"四个字段是 ID 数组"这条契约失去强制力。
- **审查轮次不可控**。2026-09-08 三份文档分别走了五、六、五轮；代码改动的审通常更细。首审 2 critical + 6 high，复审 2 critical + 6 high（两个 critical 都是我 v1.0 修订时引入的），三审 1 critical + 4 high（critical 又是 v1.1 新引入的）。**连续三轮都有我改稿引入的新矛盾**，后续每步接线都要送审，且送审前必须跑步骤号与跨章节一致性核对。
