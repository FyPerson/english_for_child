> ⚠️ **不要用文件大小或 sha256 去比对 HTML / md / py 这类文本文件**。
> 旧机器 `core.autocrlf=true`，文本文件在工作区是 CRLF、在 git 里存的是 LF，
> 新机器的换行设置不同的话本地字节数就会不一样——**这是正常的，不是文件损坏**。
> 文本文件的正确判据是 `git status` 干净（git 已经帮你归一化过了）。

跨机器稳定的基准是 **git 里存的 blob 大小**：

```bash
git cat-file -s $(git rev-parse HEAD:week01-v3.html)   # 期望 2645824
git cat-file -s $(git rev-parse HEAD:week02.html)      # 期望 648867
```

**二进制文件**不受换行影响，可以直接比对：

```bash
sha256sum assets/phonemes/*.mp3
```

## 出问题怎么办

| 症状 | 处置 |
|---|---|
| `git status` 不干净，一堆文件显示已修改 | 多半是换行符差异。`git diff` 看看是不是整文件都在变；是的话不要提交，先处理换行配置 |
| 课件打开一片空白 | 看浏览器控制台报错。base64 内嵌资源损坏的话，`git fsck` + 重新 clone |
| 音素点了不出声（第一周的六个） | 检查 `assets/phonemes/*.mp3` 的 sha256；对得上就是浏览器音频策略问题（需先有用户手势） |
| 想回到重写历史之前的状态 | 旧机器上还有 `backup/pre-reword` 分支（`fed248d`），**未推送**。真需要就去旧机器取 |

## 已知的换行符隐患

仓库目前**没有 `.gitattributes`**，旧机器是 `core.autocrlf=true`。
如果新机器（或 GPT 所在的 Linux/Web 环境）换行设置不同，编辑文本文件后可能产生
**整文件级别的假 diff**。

如果接手方要在不同平台上改文件，建议先加一份 `.gitattributes` 统一规则，
再各自重新 clone。改动前先问一句，别在有未提交内容时动它。
