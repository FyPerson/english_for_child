## 第 1 关 · 仓库拉全了吗

```bash
git clone https://github.com/FyPerson/english_for_child.git
cd english_for_child
git fetch
git status -sb          # 期望：## main...origin/main  且下面没有任何文件
git fsck --no-dangling  # 期望：无 error
git log --oneline -1    # 记下这个值，后面几关如果出问题要报给对方
```

**判据是"与远端同点且工作区干净"，不是"等于某个写死的 commit"。**
`git status -sb` 第一行不带 `[ahead N]` / `[behind N]`、下面没有文件列表，就说明
你手上的内容和远端逐字节一致——git 的内容寻址已经密码学地保证了这点，
比对文档里写死的哈希表反而更弱（那种表迟早过期）。

`git fsck` 查对象完整性，防的是传输损坏这类罕见但真实的情况。

### 抽查几个大文件确实拿到了

哈希不用比对（上面已经证明过了），但确认体积对得上能快速发现
「LFS 没配、大文件变成指针」这类问题：

```bash
ls -l week01-v3.html week02.html assets/phonemes/
```

| 文件 | 字节 |
|---|---|
| `week01-v3.html` | 2645824 |
| `week02.html` | 大于 600000（随已注入素材增长） |
| `assets/phonemes/*.mp3` | 十二个，1296–6103 |

> 仓库已用 `.gitattributes` 统一 LF（`* text=auto eol=lf`），所以文本文件在任何机器上
> `week01-v3.html` 在任何机器上都是这个字节数。`week02.html` 会随插画和音素注入增长，
> 所以这里只设防 LFS 指针的下限；最终仍以 `git status` 干净为准。

## 出问题怎么办

| 症状 | 处置 |
|---|---|
| `git status` 不干净，一堆文件显示已修改 | 多半是换行符差异。`git diff` 看看是不是整文件都在变；是的话不要提交，先处理换行配置 |
| 课件打开一片空白 | 看浏览器控制台报错。base64 内嵌资源损坏的话，`git fsck` + 重新 clone |
| 音素点了不出声（第一周的六个） | 检查 `assets/phonemes/*.mp3` 的 sha256；对得上就是浏览器音频策略问题（需先有用户手势） |
| 想回到重写历史之前的状态 | 旧机器上还有 `backup/pre-reword` 分支（`fed248d`），**未推送**。真需要就去旧机器取 |

## 换行符：已统一，无需处理

仓库根有 `.gitattributes`，规则是 `* text=auto eol=lf` —— 所有文本文件在仓库内和
工作区一律 LF，音频/图像/字体/文档显式声明为 binary 不做任何转换。

配套约束：**任何写文本文件的脚本都要用 `newline=""`**（`Path.write_text` 不传这个参数时，
Windows 上会把 `
` 翻成 CRLF，等于把统一好的换行又翻回去）。
`tools/` 下五处 `write_text` 已全部对齐这个写法，新增脚本请照做。
