# 清单生成器对复用键要整条继承；派生物的 `git status` 是免费的反向校验

**Why**：生成第三周音频清单时，我从 `build_audio.py` 的十个提取源反推出 132 条，复用前两周 raw 的 64 条只沿用了 `rate`，把前两周为 18 个词逐条调过的 `manual_trim`（词尾爆破修法：cap、cup、dip、hip、it、map、nap、nip、pig、rip、sip、snap、sock、tap、tip、top）和 `tempo`（ham、him）丢了。

三道防线都没拦住：`build_audio.py` 七项自检全绿——它查键集合、黑名单、题库、体积，不查参数继承；codex 审清单说"自洽、无必改项"——它拿不到前两周的清单，看不出继承缺失；我自己看输出也只看到"PASS"。发现它的是 `git status`：18 个本不该动的 `assets/audio_processed/*.mp3` 显示为 modified。

**How to apply**：

- **生成新周清单时，复用键整条继承上周条目**——除 `key / text / type / group / file` 之外的全部字段原样带入，不要挑字段。第三周清单生成脚本里那段"从前两周条目合并额外字段"的逻辑，第四周直接沿用。
- **任何"重新生成派生物"的步骤跑完，先看 `git status`**（`build_audio.py`、`embed_assets.py`、`port_w3.py` 都算）：不该变的文件变了 = 源头丢了东西。比自检快，比 codex 准，而且免费。第二周把"冲突按源重生成"定成规则，这条是它的反向用法。
- **给 codex 审"继承 / 移植"类产物时，brief 要附被继承的源**（上周清单、上周文件），否则它只能审内部自洽，审不出丢失。第三周首审能报出"WORD_AUDIO 还是第二周的表"，正是因为 diff 里看得到没更新；清单参数丢失它就看不到。
