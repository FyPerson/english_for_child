`python tools/project.py doctor` 一条命令就能定 Node 是否可用；验出可用后，"副机不跑校验器"的限制自动解除。

**Node 18+ 是所有副机任务的硬门槛，不只是数据层**：配图要 `build` 出 HTML 才能看图与算体量，调音的 `build_audio.py` 要注入进 `build/weekNN.html`，两者都要构建，而构建会调 `node`。Node 不可用时，副机**不能自行判定任何任务通过**——因为判定依据（构建出的 HTML、体量数字、`check --quick`）都要 Node。但不依赖构建的前置步骤仍可以做，做完交主机收口：

| 任务 | 副机能做的 | 主机补的 |

| 数据层（阶段 B） | **不能做** | —— |

**"回传截图"不是可有可无的补偿**：副机看不到图在课件里的实际效果就等于盲画，宁可慢一轮也不要凭想象继续。

## 1. 三方角色

职责分**两个阶段**。阶段 A 现在就生效；阶段 B 要等《周课件数据层交接规范 v2.0》激活（它现在是草案，激活条件见其 §8，其中第 5 条正是本文 v1.2 加副机 dry run）。**规范激活之前一律按阶段 A 执行。**

| 角色 | 阶段 A（现行） | 阶段 B（数据层交接后，最早第六周） | 两阶段都不做 |
|---|---|---|---|
| **用户** | 拍板；上课与回收数据（周检、月测、总表）；人耳听检（音素与单词发音对不对，机器验不了）；两台电脑之间的 push / pull；确认 GPT 的每一步 | 同左 | 不手改课件 HTML；不在两台电脑同时改同一周的文件；不手工合并 JSON |
| **Claude（主机）** | 课程设计与**每周数据层**；引擎升级与里程碑；周模板与主题色；音频 manifest 与首次注入；插画提示词文档；校验、冒烟、codex 审；合并冲突、重生成派生物；提交；README 与全部文档维护 | 交出数据层撰写，改为**教学设计 + 教学法过审**；其余不变 | 不出图；不替用户下听检结论；不在副机上工作 |
| **GPT（副机）** | 按提示词文档两阶段出图；按 §5 参数表调发音并跑管线；**自跑构建与检查**；按 §6 白名单保存、提交、推送；按需回答用户关于课件使用的问题 | 增加：**按数据层交接规范写 `frontend/src/weeks/weekNN.data.js`** | 手改 HTML（工具生成的改动是派生物，允许）；改任何 `tools/*.py`、`tools/validation/*`；改风格前缀；改 README 与 docs；改 `project.json`、周模板与主题色；发明新块类型、新常量、新文件名规则；解决 git 冲突 |

阶段 B 交出去的只有**数据层撰写**这一件事，**不含**：引擎改动与里程碑（铁律 2）、周模板与主题色（铁律 3）、`project.json` 周清单、教学设计与教学法过审。理由见数据层交接规范 §4.2——那些是机器验不出来的部分，第四周的五处落差全落在那里。

一句话：**Claude 定教什么、怎么教，GPT 出图、调音、（阶段 B 起）按规范把课程写成数据，用户拍板和听检，仓库是唯一的交接载体。**

**节奏**：每周的审定截止日按课程方案 §5.3"审定截止"列（第 7 周起为开课前 14 天）。阶段 A：步 1 到 5 在主机连续做完再推，步 6、7 在副机，步 8、9 回主机。阶段 B：步 1、2 在主机（教学设计与骨架），推送后步 1b、6、7 在副机，步 8、9 回主机。**一周的文件同一时间只在一台电脑上改**。

> **步 2 为什么要带一份起点 data.js**：`project.json` 一旦登记新周号，缺 `data.js` 或模板时 `build` 直接失败（实测报 `Template inventory differs from project.json`）；而未登记的周又不能单独构建（`--week 5` 报 `Unknown week`）。两条路都堵死，所以主机必须交出一个**已经能 build 通过**的骨架，副机才有可运行的仓库可改。

**`weekNN.data.js` 这个文件只有步 1b 一个所有者**：步 1 产出的是教学设计工作包（文字），步 2 产出的是能构建的起点，步 1b 才是把内容写成最终数据。阶段 A 由 Claude 连着做完步 1、2、1b，**可以跳过起点交接与它的验收**——起点交接是为阶段 B 的跨机传递准备的。

**起点四处**（2026-09-08 实测：拿 week04 造 week05 骨架，改完这四处 `build` 七个 BUILT、359 项失败 0，`check --quick` 全绿；漏改任何一处都会红）：

| # | 改哪里 | 从 | 到 |
|---|---|---|---|
| 1 | `weekNN.data.js` 的 `META.week` | 上周周次 | 本周周次 |
| 2 | `weekNN.data.js` 的 `META.storageKey` | `soundblocks-wN-1-v1` | `soundblocks-wN-v1` |
| 3 | 模板的 `@include weeks/weekNN.data.js` | 上周文件名 | 本周文件名 |
| 4 | 模板里硬编码的 `const KEY = 'soundblocks-wN-v1'` | 上周键 | 本周键 |

外加机械替换：模板里七处 `@include media/weekNN/*.js` 与头部注释。**第 3、4 处最容易漏**——只改 media 引用的话，构建出的 `weekNN.html` 用的还是上周的数据层，报「文件周次与 META.week 不一致」。

起点是**合法但未定稿**的数据：它能过契约，因为内容照抄的是一个已定稿的周；但它的词表、小书、文案全是上周的。

**光靠文字约束挡不住误发布**，所以要有机器门禁——`META.status`：

| 值 | 含义 | 门禁 |
|---|---|---|
| `scaffold` | 步 2 产出的起点，内容还是上周的 | `build` 允许；**加入 `courseWeeks` 必须失败；`release` 必须拒绝** |
| `final` | 步 1b 改完、步 9 审过的定稿 | 无限制 |

状态转换只有一个方向，由**主机**在步 9 定稿时改，副机不许自己把 `scaffold` 改成 `final`。

> **以下分两栏：左边是今天真实生效的，右边是工具补上之后才生效的。不要把右边当成已有的保护。**
>
> | | 现在（工具未支持） | 目标（待实现） |
> |---|---|---|
> | 加入 `courseWeeks` | 靠人记得不加 | 构建**失败** |
> | `release` / 打 tag | 靠人记得不打 | **拒绝**打包 |
> | 拷走 `build/weekNN.html` | 标题里的 `[未定稿] ` 前缀提示 | 同左（这一道本来就靠人眼） |
>
> **这条目前是待实现，而且过渡办法挡不住误发布，必须把风险写明**。
>
> `project.json`、`build_lessons.py`、`package` 都还不认识 `META.status`。而起点周**必须**登记进 `project.json.weeks` 才能构建（否则 `build` 报 `Template inventory differs`、`--week N` 报 `Unknown week`），登记之后 `build/weekNN.html` 就会实实在在地生成出来——**谁把它拷去上课，孩子拿到的就是上一周的词表和小书**。
>

**音频两个目录是跨周共享的**（`audio_raw/`、`audio_processed/` 里放着所有周的键），目录级白名单管不住"只改本周键"。**副机提交前**与**主机回收时**都要做键级校验，用同一段命令：

**文件名由 manifest 的 `items[].file` 声明**（不要靠 `键 + .mp3` 拼——当前值恰好如此，但那是巧合不是契约）。键名不能含空白与路径分隔符，否则 shell、文件系统与 git 路径三处都会出问题；manifest 里出现这类键先找主机改。

把下面这段存成 `tmp/verify_keys.py`（`tmp/` 已被 git 忽略）。**2026-09-08 实测过正反例**：改一个键后 `KEYS` 写对退出 0、写错退出 1 并列出多改与漏改的键。

```python
import json, subprocess, sys
# 用法: python tmp/verify_keys.py <BASE> <manifest路径> "<键1 键2 ...>"
base, mf, keys = sys.argv[1], sys.argv[2], set(sys.argv[3].split())
def from_git(ref):
    r = subprocess.run(['git','show',f'{ref}:{mf}'],capture_output=True,text=True,encoding='utf-8')
    return {} if r.returncode else {it['key']: it for it in json.loads(r.stdout).get('items',[])}
a = from_git(base)
with open(mf, encoding='utf-8') as f:                      # 比 BASE 与**工作区**，含未提交改动
    b = {it['key']: it for it in json.load(f).get('items',[])}
changed = {k for k in set(a)|set(b) if a.get(k) != b.get(k)}
extra, missing = changed - keys, keys - changed
print("  changed keys:", sorted(changed) or "none")
for f in sorted({(b.get(k) or a.get(k)).get('file','?') for k in changed}):
    print(f"resources/assets/audio_raw/{f}")                # 这两行直接就是 allowed.txt 的内容
    print(f"resources/assets/audio_processed/{f}")
if extra:   print("  FAIL extra keys changed:", sorted(extra))
if missing: print("  FAIL keys in KEYS not changed:", sorted(missing))
print("  RESULT:", "OK" if not extra and not missing else "MISMATCH")
sys.exit(0 if not extra and not missing else 1)
```

**脚本输出里不要用 GBK 字符集之外的符号**（`✓` `✗` `→` `—` 这类）。副机在 Windows 上跑，控制台是 GBK：

| 输出 | 结果 |
|---|---|
| `print('中文说明')` | 不崩，但显示成乱码 |
| `print('✗ 失败')` | **`UnicodeEncodeError` 当场崩溃**——`✗` 不在 GBK 里 |

所以判定字样统一用 `OK` / `FAIL` / `OVER` / `MISSING` 这类纯 ASCII，说明性文字用中文无妨。2026-09-08 实测确认。

文件层面的核对（与上面的键层面互补）：

```bash
# ① 允许的文件集合：直接由上面的脚本生成，它打印的就是完整路径，每行一个
python tmp/verify_keys.py "$BASE" resources/manifests/audio_manifest_wN.json "$KEYS"   | grep '^resources/' | sort -u > /tmp/allowed.txt

# ② 实际动过的音频文件。--name-status 的第一列是状态，**先看状态再比路径**
git diff --name-status --find-renames "$BASE"..HEAD -- 'resources/assets/audio_*' > /tmp/st.txt
git diff --name-status --find-renames             -- 'resources/assets/audio_*' >> /tmp/st.txt
git diff --cached --name-status --find-renames    -- 'resources/assets/audio_*' >> /tmp/st.txt
grep -E '^(D|R)' /tmp/st.txt && echo "有删除或重命名，直接拒绝"    # 音频只该新增或修改
cut -f2- /tmp/st.txt | sort -u > /tmp/actual.txt                  # 去掉状态列，只剩路径

# ③ 两个集合都是纯路径，这时才能比
comm -13 /tmp/allowed.txt /tmp/actual.txt                          # 有输出 = 越界，停下
```

**`comm` 的两个输入必须格式一致**（都是纯路径、都 `sort -u` 过）；把带状态列的行直接喂给它，比出来的结果没有意义。

副机 `git add` 按 ① 算出的具体路径加，**不要 `git add resources/assets/audio_raw`**（会把别的周未完成的键一起暂存）。`comm`、`grep` 在 Git Bash 里可用；换成别的 shell 请先确认。

**要两个基准，不是一个**——§3 的并行规则允许主机在副机干活的同时提交第 N+1 周，如果只用一个交接基准，副机 `pull` 之后主机那些合法提交会被算进"副机改了什么"，造成误判。

| 变量 | 谁记 | 什么时候记 | 用来干嘛 |
|---|---|---|---|
| `HANDOFF_BASE` | 主机 | 推送交接包时 `git rev-parse HEAD`，写进工作包（§4） | 主机回收时定位这一轮交接的起点 |
| `LOCAL_BEFORE` | 副机 | **每次开工时**，以及**每次 `git pull` 成功之后**（不是之前） `git rev-parse HEAD` | 副机自查"我这一轮改了什么" |

**记录时机是 pull 之后，不是之前**——pull 会把主机的提交并进来，HEAD 随之前进。若在 pull 前记，`LOCAL_BEFORE..HEAD` 就会把主机那些提交也算成副机的改动。第五稿这里写反了，已纠正。

配套两条：

- **pull 前工作区要干净**：先提交或 `git stash`。带着未提交改动 pull，改动虽在工作区，但 `LOCAL_BEFORE..HEAD` 只看提交，范围核对会漏——所以文件层面的核对要**同时看 `git diff`、`git diff --cached` 和 `BASE..HEAD` 三处**（上面 ② 就是这么写的）。
- **pull 前已经有自己的提交**：那 `LOCAL_BEFORE` 在 pull 后重记会把它们排除在外。此时改用 pull 前记的那个 SHA，或者干脆先 push 掉自己的提交再 pull。两种做法选一种，写进当次上报。

```bash
# 副机自查（只看自己的改动，不含 pull 进来的主机提交）
git diff --name-only "$LOCAL_BEFORE"..HEAD

# 主机回收（按作者过滤掉自己的并行提交）
git log --format='%h %an %s' "$HANDOFF_BASE"..HEAD          # 先看清这段里有谁的提交
git diff --name-only "$HANDOFF_BASE"..HEAD                  # 全部变更
```

主机那段里若混着自己的并行提交，按提交逐个核对，**不要把整段变更都算到副机头上**。

没记基准时的兜底（可能误判，只作参考）：`git log -1 --format=%h --grep=Claude-Session`。

本文所有代码块按 **Git Bash** 写。`<BASE>` 一律替换成实际的 SHA，不要留尖括号。PowerShell 下的等价写法：

```powershell
$BASE = git rev-parse HEAD                       # 记录基准
git diff --name-only "$BASE..HEAD"               # 核对范围
```

出现 `tools/*.py`、`tools/validation/*`、`docs/`、README 或其他周文件的改动，把这些文件恢复，只保留白名单内的改动，并在提交说明里记一笔。

**恢复方式按是否已推送分两种**：

- **未推送**（只在副机工作树里）：副机自己 `git checkout <BASE> -- <越权路径>` 即可。**这里的 `<BASE>` 用 `LOCAL_BEFORE`**（自己这轮的起点），不是 `HANDOFF_BASE`——用后者会把主机在这期间的并行提交一起回滚掉。
- **已推送**：**只能由 Claude 在主机建一个新的纠正提交**，用 `git checkout <BASE> -- <越权路径>` 取回正确版本后提交。**禁止 `reset`、禁止强推**，也不要让副机自行处理——历史已经共享，改写历史会让另一台机器的克隆失效（2026-09-07 那次历史重写是主机统一执行并通知全员重新 clone 的，不是常规操作）。

### 6.4 分支与冲突

- 只用 `main`，不建长期分支。同一周的文件同一时间只在一台电脑改。
- **冲突按真相源裁决，不按扩展名**：源 = manifest、`resources/assets/audio_raw/`、PNG、`frontend/src/weeks/weekNN.data.js`；派生 = `resources/assets/audio_processed/`、注入后的 HTML。冲突由 Claude 在主机按周次和键合并源文件，然后统一重跑 `build_audio.py`、`embed_assets.py` 重生成派生物并校验。用户和 GPT 不手工合并 JSON 或 HTML。
- push 被拒：先 `git pull --no-rebase`，无冲突再 push；有冲突停下交主机。

### 6.5 不跨机的东西

Claude 本机记忆（真相在仓库 `docs/项目记忆/`）；`tmp/`（已忽略，codex 运行产物）；`.claude/settings.local.json`（已忽略）。Claude Code 在新机器上开工：仓库自带的 `/handoff`、`/tidy-docs` 自动加载；第一条动作是读 README，不是读会话历史。

### 6.6 副机开工 dry run（第一次，或换机器后）

**这是阶段 B 的激活证据之一**（数据层交接规范 §8 第 5 条）。逐条跑，把输出留给主机存档：

```bash
# ① 环境。阶段 B 的最低门槛是 Python 3.10+ 与 Node 18+
python --version && node --version
python tools/project.py doctor             # 见下：这一条有两种可接受结果

# ② 同点且干净
git fetch && git status -sb                # ## main...origin/main，下面无文件

# ③ 记下基线，用来证明历史周只读
git rev-parse HEAD > /tmp/base.txt
python tools/project.py build              # project.json 声明的每周与入口都 BUILT，末尾失败 0 项
python tools/project.py check --quick      # 全绿

# ④ 构建产物清单：build/ 里只该有这些，且一个都不该进 git
ls build/                                  # course.html index.html weekNN.html …
git status --short                         # 空。build/ 被忽略，构建不该弄脏工作区

# ⑤ 演练一次白名单。用唯一临时 worktree，不碰正式工作区
WT="$(mktemp -d -p .. dryrun-wt-XXXXXX)" && rmdir "$WT"   # 借 mktemp 取唯一名字，worktree add 要求目录不存在
test ! -e "$WT" || { echo "目录已存在，换一个名字"; exit 1; }
git worktree list                          # 先看清现有 worktree，出现遗留的先处理
git worktree add "$WT" HEAD
(
  cd "$WT"
  echo '// dry-run marker' >> frontend/src/weeks/weekNN.data.js
  git diff --name-only                     # 只能输出 frontend/src/weeks/weekNN.data.js
  git checkout -- frontend/src/weeks/weekNN.data.js   # 先撤掉 marker
  git status --short                       # 必须为空，否则不要往下走
)
git worktree remove "$WT"                  # 工作区已干净，不需要 --force；失败就保留并上报
git worktree list                          # 确认已清理干净
#   2026-09-08 在主机 Windows + Git Bash 上实跑通过：mktemp 取名、add、diff 只出一个文件、
#   checkout 撤销后 status 为空、remove 不需要 --force、清理后只剩主工作区。

# ⑥ 用 ③ 记的 BASE 断言历史周与受保护路径一字未动
git diff --exit-code "$(cat /tmp/base.txt)" -- frontend/src/shared tools docs project.json
#   退出码 0 才算过；非 0 说明碰了不该碰的
git status --short                         # 回到空
```

六步全过才算副机具备阶段 B 的执行条件；把每步输出留给主机存档。任一步不过，停在那里告诉主机，不要跳过继续。

以上命令按 **Git Bash** 写。PowerShell 下 `$(cat ...)` 要换成 `(Get-Content ...)`，`printf` 换成 `Add-Content`。

**第 ① 步的 `doctor` 有两种可接受结果**，按副机实际环境选一种，选了哪种要写进上报：

| 结果 | 判定 | 后续 |
|---|---|---|
| 末行 `PASS environment, Node.js >= 18 and Chromium` | 通过 | 正常继续 |
| 报 `Browser dependency unavailable: …`，但 `python --version` ≥ 3.10、`node --version` ≥ 18、`check --quick` 全绿 | **有条件通过** | 把 `doctor` 的完整失败输出上报主机存档；完整回归只能在主机做 |

`check --quick` 确实不需要 Chromium——`tools/run_checks.py` 里浏览器套件挂在 `if not args.quick` 分支下（第 45、65 到 68 行），`--quick` 时打印 `SKIPPED: browser suites`。所以上面第二种结果是成立的，不是权宜之计。

**其他任何失败形态都算不通过**（Python 或 Node 版本不够、`check --quick` 红）。

**`doctor` 目前只有一个总结果**：它会实际启动一次 Chromium，起不来就 `SystemExit`，无法只验基础环境。

现行口径：

- **能装就装**（`python -m playwright install chromium`），让 `doctor` 干净通过，这是首选。
- **确实装不上**：`doctor` 会红，此时以 `python --version`、`node --version`、`check --quick` 全绿作为阶段 B 的替代门槛，并把 `doctor` 的失败输出上报主机存档。完整回归（`python tools/project.py check`，含浏览器测试）无论如何都在主机做。
- 这是个**已知的工具缺口**：`doctor` 应当提供一个只验基础环境的参数。在它加上之前，按上面两条走，不要改文档去迁就。

**体量护栏在副机侧怎么判**（铁律 10）：**这是 §3.1、§3.2、§3.3 三份清单每次都要跑的一步**，不是可选检查。

```bash
python tools/project.py build
python - <<'PY'
import json, os, sys
budget = json.load(open('project.json', encoding='utf-8'))['sizeBudgetMB']
bad = False
week_n = 5                                                  # 换成本周周号
for name, key in [(f'week{week_n:02d}.html', 'week'), ('course.html', 'course')]:
    p = os.path.join('build', name)
    if not os.path.exists(p):
        print(f'{name}: MISSING (not built yet)'); bad = True; continue
    mb = os.path.getsize(p) / 1048576
    over = mb > budget[key]
    print(f'{name}: {mb:.2f} MB / budget {budget[key]} MB -- ' + ('OVER' if over else 'OK'))
    if over: bad = True
sys.exit(1 if bad else 0)
PY
#   退出码 0 = 两个预算都没触线；非 0 = 有 OVER 或 MISSING，停下上报，不要自己删图或压缩。
#   判定字样用纯 ASCII，理由见 §6.3 那张表。
```

**周文件和合并入口两个预算都要看**（`sizeBudgetMB.week` 与 `.course`），换算按 1 MB = 1048576 字节。

**触线的处理是停下上报，不是自己删图或压缩**：把实际字节数、本周新增了多少张图报给主机，等主机归因。`check` 里的护栏作业是主机侧的最终门禁，副机这一步只是提前发现。副机无法判定时（例如媒体尚未全部注入），**不要声称护栏已通过**，如实写"未判定"。

**配图与调音还要额外装**（不在 `requirements-dev.txt` 里，因为不属于普通构建）：


## 7. 冲突与优先级

- **真相源优先级**：**定稿提交里的版本化源码**（`frontend/src/`、`resources/`、`tools/`）> 周课件规范 > 课程方案 > 本文 > design-doc。"实作优先"只指规范写漏或写错的地方以实作为准并回改规范；实作里的已知 bug 不因此成为规范。
  生成的 HTML **不是**真相源——它是源码在某个提交上构建出来的产物，只能用来核对构建结果。v1.1 写的"上一周定稿 HTML 的实作"是生成物不入库之前的口径，已过期。
- **没有同型周可抄时**（例如第一次出现某个周型）：由 Claude 建 scaffold，**不许猜**。周型的定义与选取规则见数据层交接规范 §4.3。
- **GPT 的产物与规范冲突**：规范赢。GPT 提的"优化建议"一律先记成 issue 由用户拍板，不直接落地。
- **谁能改工具**：只有 Claude 改处理链、校验器、注入脚本；GPT 与用户只改 manifest 参数和素材文件。
- **谁能改文档**：本文、周课件规范、课程方案由 Claude 改并走版本号；提示词文档每周一份不回改旧周；README 只由主机改。
