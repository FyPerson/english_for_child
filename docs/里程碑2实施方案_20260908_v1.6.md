### 0.2 本方案要求对规范做的修改

实施第 0 步执行，先于一切代码改动：

1. 规范 §4.1 第 17 条 `DATA-ASSESS-01` 的状态从「待实现（里程碑 2 同期）」改为「**部分实现（里程碑 2：最小路由）/ 待实现（里程碑 2b：完整矩阵）**」，按 §0.3 的两段切分写明各自内容，并在 §8 给里程碑 2b 的截止日写为 **2026-10-31**（2026-09-08 用户拍板）。推算依据：课程方案 §5.3 的 W5 自 09-28 起、每周一轮，则 W9 为 10-26 至 11-01、**W10 自 11-02 开始**；2b 的交付物含 W10 fixture，所以必须赶在 W10 开课前就位。
2. 规范 §8 生效条件第 2 条拆成两条：**W5 fixture 与 `assessmentMode` 最小路由留在里程碑 2**；W10 / W20 两个 fixture 与完整矩阵改挂里程碑 2b。
3. 规范 §8 生效条件第 1 条补全本次实际范围：除四个字段改数组和 `check_data.js` 六处外，加上墙语义统一、歧义检测与 `segments` 消费接口、`assessmentMode` 最小路由、`L` → `grapheme` 收敛。
4. **规范 §3 的"最长匹配"要限定**（六审 H-1）。规范第 127 行写的是「按已教字位集合**做最长匹配**」——把最长匹配写成了算法本身；第 129 行的"多解"也停在局部候选层面。而本方案 §3.2 要求的是**枚举完整解析集合、多于一解即失败**，最长匹配只能当剪枝。两份文本并存，两个实现者会分别做出贪心最长匹配和全局唯一性检测，**同一个词在浏览器与 Node 两端得到不同结果**。

   所以第 0 步同步修订规范：删除或限定"最长匹配"的表述，改为**以所有完整解析的基数判定 0 解 / 唯一解 / 多解**，并写明最长匹配仅可作搜索优化、不得改变解析集合。把 `abc` 在 `a`/`ab`/`bc`/`c` 下有两解的例子同时写进规范与 fixture。**此项必须在第 2 步实现接口之前定死。**
5. **规范的 `SOUNDS` schema 删除 `L`**（五审 H-1）。规范现在两处同时写着 `L` 与 `grapheme`——§3「`SOUNDS` 单条」的示例是 `ai:{L:'ai', grapheme:'ai', …}`，§3「12 个常量」表里是 `{字位ID:{L,grapheme,ipa,…}}`（第 158 行），而字段说明只解释了 `grapheme` 没解释 `L`。**按 v1.3 的文本直接删 `L`，代码会符合方案却违反被声明为权威的规范。** 所以第 0 步就要把规范的 schema、示例、字段说明统一改成只有 `grapheme`（必需、唯一显示字段），并注明旧数据的迁移要求。规范改完之后，第 4a 步才执行代码与数据的重命名。

规范 §8 的其余条件（`noveltyPolicy` 逐周取值、三方分工 v1.2 dry run、第五周实跑一轮）不动。

### 0.3 `DATA-ASSESS-01` 为什么不能整体拆出

v1.0 把它整体拆到里程碑 2b，复审 C-1 判为**阻断性矛盾**，本地核实成立：

- `assessment_contract.js:5` 是 `if(d.META.week < 4) return []`——**W5 会进入完整校验**，`:7` 要求 `RESERVED`、`RESERVED_RETEST`、`PROBE_A`、`PROBE_B`、`GLOBAL_RESERVED` 五个池齐全，`:10` 要求 `RESERVED` 与 `RESERVED_RETEST` 各 5 词，`:13` 要求 `GLOBAL_RESERVED` 完整保留附录 B 的 40 词。
- 而规范 §4.3 矩阵里 weekly 周**只允许 `RESERVED`**，正是要消除「普通周被迫携带无意义的全局常量」。
- `assessmentMode` 字段**目前全仓 0 处引用**，尚不存在。

所以整体拆出的结果是：W5 要么塞进一堆无意义常量才能过校验，要么根本装配不了。**基础假设「拆出后不阻塞 W5 装配」不成立。**

**改为两段切分**：

| 部分 | 归属 | 内容 |
|---|---|---|
| **最小路由** | **里程碑 2** | `META` 新增 `assessmentMode` 字段；`validateAssessment` 的门槛从 `week < 4` 改为按 `assessmentMode` 路由；weekly 周只要求 `RESERVED`。**这是 W5 能装配的前提** |
| **完整矩阵** | 里程碑 2b | monthly / stage / annual 三种模式的全部常量组合、`RESERVED` 释义来源、W10 / W20 两个 fixture |

W5 自己的 fixture 属最小路由部分，随里程碑 2 落地。

**最小路由阶段的临时行为必须逐档定义**（五审 H-2）。只写"weekly 走新逻辑、其余走旧逻辑"会留两个坑：W10 / W20 可能按周号旧逻辑假绿；全部拒绝又会打断 W4 现有的 monthly 回归。所以：

| `assessmentMode` | 里程碑 2 阶段的行为 |
|---|---|
| `weekly` | 执行规范 §4.3 矩阵 weekly 列的完整校验（必需 + 8 项禁止） |
| `monthly` | **仅 `assessmentMode:'monthly' && META.week === 4`** 可进入兼容路径，执行下表逐项枚举的检查集合；**其他 monthly 周一律报「里程碑 2b 前不支持」** |
| `stage` / `annual` | 返回固定的**「里程碑 2b 前不支持」错误**，不放行也不假装通过 |
| 缺失 / 非法值 | **一律失败** |

**禁止用默认分支回落到旧的周号逻辑**——那正是 `DATA-ASSESS-01` 要废掉的东西。

**W4 monthly 兼容集合逐项枚举**（六审 H-2）。v1.4 写的"仅执行 `week === 4` 分支内容"是错的：`validateAssessment` 在走到那个分支之前还有一整批公共检查，只搬分支会让 W4 悄悄失去它们。定义为**「当前校验器对合法 W4 实际执行的全部检查」**，逐项列出：

| # | 检查 | 现位置 |

| 1 | 五个池必须都是数组 | `:8` |
| 2 | `RESERVED` 与 `RESERVED_RETEST` 各 5 词 | `:10` |
| 3 | `PROBE_A`/`PROBE_B` 数量与段末周匹配（W4 非段末，须为 0） | `:12` |
| 4 | `GLOBAL_RESERVED` 完整保留附录 B 的 40 词 | `:13` |

| 6 | **池间互斥**（同一词不得同属两池） | `:18` |

**实现约束**（采纳七审建议）：不要照着这张表重新实现。**先把现有 W4 路径原样提取为独立函数，用「重构前后错误集合完全一致」的特征测试锁定**，再接到 `assessmentMode:'monthly' && week===4` 上。表只作为核对清单，特征测试才是门槛。

第 7 项的已教 CVC 判定与第 15 项的未教字位判定都是字符级的，改走字位后一并处理——见 §2.2 矩阵「字位数」与「陌生度」行。

## 1. 为什么现在做

课程方案 §5.3：W5（09-28 起）教 `ai` `j`，技能重点是"两个字母一块积木"。§9.2 对里程碑 2 的描述是：

> 拆词按字位表而不是按单字母；`SOUNDS` 键允许双字母；G2、G3、G4、G5、点亮墙、快闪、校验器同步。现引擎按单字符拆词，第 4 组六块积木有五块摆不出来。

审定截止 09-27。**不做这个，W5 出不来。**

「五块摆不出来」的真实机制在 §2.2 的槽位长度一行：G4 按**字符长度**建槽，`rain` 建四个槽却只有三块积木，永远填不满。

### 2.3 `rack` 是多重集，不是集合

四周实际值（2026-09-08 实测）：

| 周 | `wallLetters` | `rackG4` | `rackG5` |
|---|---|---|---|
| W1 | `satipn` | **`ssaattiippnn`**（每字母两块，12 块） | 同左 |

**第一周每个字母有两块积木**，因为它要摆 `nn`、`pp` 这类。迁移成数组时**必须保留重复项**——用 `Set` 或去重会让第一周的 G4/G5 直接摆不出词。

首审 H-3 补充：保留重复只是必要条件，还必须把槽位长度、数组比较、表面串生成、白名单查询一并改成字位安全，见 §3.1。

### 2.4 墙语义统一的实际后果

规范 §3 定义 `wallLetters` 是「墙上**完整**的积木集合，有序」，等于 `SOUNDS` 全部键；本周新点亮的由 `newPatterns` 表达。现状按周型跳变。统一后：

| 周 | `SOUNDS` 键数 | `wallLetters` 现值 | 统一后 | 后果 |
|---|---|---|---|---|
| W1 | 6 | 6（`satipn`） | 6 | 不变 |
| W2 | **13**（12 + 追加的 `k`） | **7**（`ckehrmd`） | **13** | **墙 7 块 → 13 块** |
| W3 | **19**（18 + 追加的 `k`） | **6**（`goulfb`） | **19** | **墙 6 块 → 19 块** |
| W4 | 19 | 19 | 19 | 不变 |

**这是已交付课件的呈现改变，不只是类型迁移。** 第二、三周的孩子会看到墙上多出此前学过的积木（未点亮态），这正是规范想要的"墙是完整集合、新的靠动画区分"。

两件事必须同时做，否则改了等于没改：W2/W3 的模板是**硬编码字面量**，不读 `META.wallLetters`——只改 data.js，页面还是显示旧的 7 / 6 块。

`k` 是**追加键**（`week02.data.js:106`、`week03.data.js:150` 的 `SOUNDS.k = Object.assign({}, SOUNDS.c, { L:'k' })`，c/k 同音共享录音但是两块积木）。分词函数取字位表必须在追加之后，否则 `k` 不在表里。反解析侧已经支持——`load_data.js:17` 有 `raw.match(/^SOUNDS\.\w+ = Object\.assign\(.*?\);$/gm)` 专门收这类追加声明。

**墙的顺序需要独立真相源**（三审 H-3）。规范既要求 `wallLetters` 顺序有教学意义，又明确说不依赖对象键枚举顺序——那么校验时的"期望顺序"不能取 `Object.keys(SOUNDS)`（违反后一句），也不能取 `wallLetters` 自己（循环校验）。

**真相源定义为：按 `project.json` 的周序，依次累计各周 `newPatterns`，同周内按 `newPatterns` 自身顺序追加。** `DATA-WALL-01` 拿 `wallLetters` 与这个独立序列比，而不是与 `Object.keys(SOUNDS)` 比。

**取数规则写死**（四审 H-4），否则单文件 fixture、历史缺周、别名跨周会产生不确定结果：

- 计算函数是**纯函数**，输入为**按周排序的规范化周记录数组**，不直接读工作树——否则独立 fixture 会受仓库现状影响而不可复现。
- **当前被校验的文件替换仓库里的同周记录**，不重复计入。
- 周号必须**连续且唯一**，不满足即失败。
- 追加时**重复即错误**，不是静默去重。
- **别名派生键**（`k` 这类）**必须出现在某周的 `newPatterns` 里**，与本体同周按数组顺序表达（六审 M-6 拍板）。不引入额外的插入元数据，也不靠 `Object.assign` 的语法形状去猜。
- 第 7 步启用该校验时，**同时迁入 W1–W4 的 `newPatterns` 数组**——这个字段和 `assessmentMode` 一样是本次新增，不先迁就没有期望序列可算。

### 2.5 基线比对四项

fixture 里记四项：`sha256`、`skeletonSha256`、`declarationOrder`、`media`。但**自动门槛只有后三项**——`baseline.py:210-224` 的 `differences()` 只比较 `skeletonSha256`、`declarationOrder` 与 `media`，**不比较周 `sha256`，也不比较 `course.sha256`**（三审 H-4）。

所以口径写清楚：**`sha256` 是审计元数据，不是自动门槛**。改 `META` 会改变 data.js 内容进而改变产物，`sha256` 与 `skeletonSha256` 都会变，但校验器只会因 `skeletonSha256` 变化而报错。基线仍必须在改造完成后重取，验收按工具真正检查的三项写（§5）。

首审 M-11 补充：`baseline --create` 会先构建并要求构建**不产生 tracked 变更**，所以重取之前必须已提交全部受版本控制的派生物，工作树干净——否则该命令直接拒绝。

## 3. 设计决策

### 3.1 三层概念：字位 ID / 字形 / 表面串

首审 C-1 的根因是 v0.1 只想着"把字符串换成数组"，没区分这三层。定义如下，本方案后文一律按此用词：

| 层 | 是什么 | 例 | 用在哪 |
|---|---|---|---|
| **字位 ID** | `SOUNDS` 的键，稳定标识 | `'r'`、`'ai'`、将来的 `'oo_short'` | 槽位、比较、rack、四个字段 |
| **字形 `grapheme`** | `SOUNDS[id].grapheme`，它实际的字符串 | `'r'`、`'ai'`、`'oo'` | 一切显示：tile 文字、ARIA、CSS 类 |
| **表面串** | 词本身，等于各字位字形依次拼接 | `'rain'` | 查词：`W` 的键、G5 白名单、`confirms` 键、音频键 |

**`grapheme` 在实作里已经存在，叫 `L`**（四审 H-3）。`SOUNDS` 每条都有 `L` 字段，`week02.data.js:106` / `week03.data.js:150` 的 `SOUNDS.k = Object.assign({}, SOUNDS.c, { L:'k' })` 改的正是它——c 与 k 共享发音数据、只有显示字母不同。现在全部字位是单字母，所以 **ID === `L`**，两者随便混用都不出错；`oo_short` 一出现就分家。

**本次拍板：`L` 就是 `grapheme`，做重命名**。`SOUNDS[id].grapheme` 是唯一字形字段，`L` 不保留为别名——留着会让"到底该读哪个"永远有歧义，而现在四周数据的 `L` 值与键完全相同，重命名是纯机械替换，代价最低。校验器加一条：`SOUNDS` 条目不得再出现 `L` 字段。

**影响面（2026-09-08 全仓扫描，按属性访问 / 字符串键 / 解构 / 派生赋值四种模式）**：

| 类别 | 位置 | 处置 |
|---|---|---|
| 生产代码 | `render-blocks.js:46` `tileHTML(SOUNDS[f].L,…)`、`:49` `forms.map(f=>SOUNDS[f].L).join(' 和 ')`、`games.js:1154` flash 的 `s.L` | 改走 `graphemeLabel(id)` |
| **校验器** | **`check_data.js:83` `ok(s.L && s.ipa && …, 'SOUNDS.${k} 缺 L/ipa/type')`** | **改判 `grapheme`**。这条是硬门槛，不改则删 `L` 当场全红 |
| 数据 | 四周 `weekNN.data.js` 每个 `SOUNDS` 条目（week04 是 `"L": "s"` JSON 风格 19 条，前三周是 `L:'s'` 紧凑风格）；`week02.data.js:106`、`week03.data.js:150` 的 `Object.assign({}, SOUNDS.c, { L:'k' })` | 随第 4a 步重命名 |
| 测试 fixture | `tests/fixtures/week02-data.js:108`、`week03-data.js:152` 的同一句派生 | 同步 |
| 权威规范 | `周课件数据层交接规范 v2.0` §3 示例与第 158 行的 12 常量表 | **第 0 步先改**，见 §0.2 **第 5 条** |
| 归档文档 | `声音积木周课件设计规范_20260831_v1.0.md:222/237/244`、`第三周数据层交接_20260901_v1.0.md:82` | **不改**：已归档的历史文档，改了反而与它们描述的历史实作不符 |
| 遗留工具 | `tools/legacy/w2data.py:107` | **不改**：`tools/` 与 `project.json` 均无引用，纯归档 |

**验收门槛是数据与代码双保险**（六审 M-4）。四模式扫描是**发现手段**，不能单独当完成证明——它漏得掉计算属性访问、别名后访问、辅助函数间接读取。所以：

1. **运行时 schema 断言**（兜底）：加载全部现役周与 fixture 后，递归断言每个 `SOUNDS` 条目**没有自有键 `L`**、且**有合法 `grapheme`**。
2. **源码扫描**：用 AST，或明确覆盖 `.L`、`['L']`、`["L"]`、对象字面量键、解构、`Object.assign` 派生六种写法；归档目录走**显式排除清单**，不靠路径猜。

两条都过才算第 4a 步完成。

**硬规则**：

- 凡是"有几块""摆对没有"——用 **ID 数组**，逐项比较，不用 `join('')`。
- 凡是给人看的——用 **grapheme**，不要把 ID 直接渲染出去。单字母字位两者相同，所以现在看不出差别；`oo_short` 一旦出现，直接泄漏到孩子界面。
- 凡是查表——用 **表面串**，由 `surfaceOf(ids, SOUNDS)` 生成，不靠 `slots.join('')` 偶然成立。

**第四条：机器身份与外部键**（复审 M-10）。上面三层覆盖的是数据转换，但还有一类消费是"拿什么当标识符"：

- **确认状态、槽位、DOM `data-*`、业务比较** → 用稳定 **ID**。同形多音若用 grapheme 当键，`oo_short` 和 `oo_long` 会共享确认状态。
- **词级持久状态** → 用规范化**表面串**。
- **音频** → 必须经 `audioKey` 解析，不能拿 ID 或 grapheme 直接拼文件名（`k` 与 `c` 共享录音正是靠它）。
- **CSS 类名** → 不得直接拼接未经转义的 ID；`oo_short` 这类带下划线的还好，将来若有特殊字符会产生非法或难选择的选择器。

这四类已列进 §2.2 迁移矩阵。

G4 因此改成：先取目标词的字位序列 `targetIds`，槽数用 `targetIds.length`，判定逐项比较 ID；G5 的 `slots` 存 ID，查词前先过 `surfaceOf`。

**文案同步改**：`games.js:390` 的「听到的词是 N 个字母」改成「N 块积木」。课程方案 §5.3 的说法就是"两个字母一块积木"，说"字母"会和教学口径打架。

### 3.2 `segmentWord` 契约

v0.1 的 `tokenize(word, patterns)` 只有签名没有语义，`patterns` 到底是 ID 数组、字形数组还是映射也没定义（首审 H-3）。改为：

```js
segmentWord(word, sounds, explicitSegments?) -> string[]   // 字位 ID 数组
```

契约逐条写死：

- **匹配依据固定为 `SOUNDS[id].grapheme`**，不是键本身——`oo_short` 这个键不会出现在任何单词里。
- **规范化**：先 `toLowerCase()`（`check_data.js:133` 现在就是这么做的），规范化后的串用于匹配。
- **歧义按「整词有几种完整分词」判，不是按「当前位置有几个同长度候选」**。复审 H-3 指出 v1.0 的「最长匹配优先 + 同长度多解抛错」只能抓局部冲突：若字位表含 `a`、`ab`、`bc`、`c`，则 `abc` 有 `ab`+`c` 与 `a`+`bc` 两种完整解，**首段长度不同**，局部规则一个都抓不到。规范 §3 要的是「出现多解即失败」。
  所以契约是：**求整词的全部可行分词——0 解报未知，恰好 1 解返回，多于 1 解报歧义**。最长匹配只能用作剪枝或在已证明全局唯一后的选择依据，不能用来消灭合法的较短起始路径。
- **复杂度有界**（复审 M-12）：用按 offset 记忆化的动态规划或 trie，状态只保留「0 解 / 唯一解 / 多解」三态加有限几个候选用于报错，**不枚举全部解**，避免前缀高度重叠时的指数回溯。
- **未知区间 → 抛未知错误**。**空串 → 抛错**。
- **`explicitSegments` 的完整校验**（复审 H-5）：必须是非空字符串数组；每个元素必须是 `sounds` 的**自有键**；`surfaceOf(explicitSegments)` 必须等于规范化后的 word。任一条不满足即抛结构化错误。`displayOnWall:false` 只影响墙展示，**不影响分词资格**。
- **`surfaceOf`、`graphemeLabel`、`soundType` 遇到未知 ID 一律抛同一种结构化错误**，不返回 `undefined` 让它在下游变成难定位的异常。
- **错误是结构化对象**，带 `{word, offset, candidates}`，让校验器能指出是哪个词的哪个位置需要消歧。浏览器构建可只带精简错误码，Node 校验器补详细位置说明。
- **输入 schema 先验**（三审 M-7）。建索引前先校验，不合法立即抛：`word` 必须是字符串；`sounds` 必须是普通映射且**只读自有键**（不走原型链）；每项的 `grapheme` 必须是非空字符串，且规范化后仍非空。**空 grapheme 必须在进 DP 前失败**——否则会产生零长度转移，DP 状态图出现自环而不前进。
- **`offset` 的口径**：以**规范化后**的串计，用 UTF-16 索引，浏览器与 Node 必须一致。
- **歧义错误的定位必须确定**（七审 M-4）。全局多解时两条解析在不同位置分叉，若不规定，浏览器与 Node 会报出不同的 `offset` 与候选——两端都判失败，但错误契约不一致。规定：**`offset` 取两条见证解析的最早分歧点**（规范化串的 UTF-16 索引），`candidates` 按**稳定排序**输出。测试要同时断言错误码、`offset` 与候选集合，不能只断言"抛错了"。
- **确定性**：同输入同输出，不依赖 `SOUNDS` 的键枚举顺序。

配套导出：

```js
surfaceOf(ids, sounds)            // 字位 ID 数组 → 表面串
graphemeLabel(id, sounds)         // 字位 ID → 显示字形
soundType(id, sounds)             // 字位 ID → 'c' | 'v'
normalizeIdList(value)            // 迁移期双读，见 §3.5
colorStrictWord(word, ctx)        // 单词：分不出就是数据错误，抛
colorPlainText(text, ctx)         // 纯文本句子：逐段转义，未知词降级
colorRichText(html, ctx)          // 受限富文本：白名单解析后只着色文本节点
```

**所有会拆词的上层入口收的是解析上下文，不是裸的 `sounds`**（四审 C-2）：

```js
ctx = { sounds, segmentsOf(normalizedWord) }
```

**`segmentsOf` 的调用契约同样写死**（五审 H-4），否则 plain / rich 各自采用不同的规范化方式，显式消歧仍会丢：

- 着色器**先用唯一的 `normalizeWord` 得到查表键**再调用，传进去的一定是规范化后的词，不是原始 token。
- 找不到词条返回 **`undefined`**，表示"无显式分段"，走自动分词。
- 返回非 `undefined` 时，**必须再交给 `segmentWord` 走完整校验**（§3.2 的 `explicitSegments` 那套：非空字符串数组、ID 是自有键、表面串一致），不能直接信任。
- 返回的数组**不得被调用方就地修改**。

测试覆盖四类：大写 token、同一个词在一段文本里重复出现、一段 HTML 里有多个不同的消歧词、未知词降级。

v1.2 把三个着色接口写成 `(text, sounds)`，**没有任何通道能拿到 `W[word].segments`**——遇到 `oo_short`/`oo_long` 时，规范要求"用显式 `segments` 消歧"的数据在渲染层重新变成歧义错误，等于 §3.4 说的"冻结消费接口"根本没做完。`colorStrictWord` 必须读显式 segments；`colorPlainText`/`colorRichText` 里的每个 token 也要能查到对应词条。要加同形多音词在 strict / plain / rich 三条路径都正确着色的用例。

底层可以另有一个收预编译索引的纯函数做性能优化，但**对外只暴露上面这组**，不暴露含义不明的 `patterns`。

`sounds` 参数必须传**追加键之后**的 `SOUNDS`（§2.4 的 `k`）。

### 3.3 句子与正文的着色

`colorWord` 有 42 个调用点，其中三处传的是含空格标点的整句（书名、书页正文）。对整串做严格分词必然抛错。

结果会进 `innerHTML`，所以**按输入是不是富文本拆成两个接口**（复审 H-6）：

| 接口 | 输入 | 规则 |
|---|---|---|
| `colorStrictWord(word, sounds)` | 单个词（词卡、tile、G2 积木态） | 走严格分词，分不出来就是数据错误，**抛结构化错误** |
| `colorPlainText(text, sounds)` | 纯文本句子（书名、书页正文） | 先保留分隔符地切词，逐词尝试分词；能分的着色，不能分的降级为原样；**每一段非着色文本必须 HTML 转义**后再拼回 |
| `colorRichText(html, sounds)` | 允许标记的字段 | 按白名单解析后**只对文本节点着色**，标签结构保留 |

**白名单是完整结构，不只是标签名**（三审 M-8）：`<b>` 无属性、`<br>` 无属性、`<span>` 仅允许 `class` 且值严格等于 `en`。**其余标签与任何其他属性一律拒绝，不是保留**——只限制标签名挡不住 `span` 上的事件属性、`style` 或危险实体。

**校验顺序固定为「先解析 → 再检查解析后的元素与属性 → 最后受控序列化输出」**（四审 M-7）。顺序反了会出事：先扫源码字符串再交给 `DOMParser` 解码，实体可以在解码后改变文本或属性语义。同时**拒绝注释节点、命名空间元素和任何非白名单节点类型**。

测试比较**规范化后的 DOM 语义**，不要求浏览器与 Node 逐字节序列化一致。用例含实体编码的属性、嵌套标签、畸形标签。

**42 个调用点必须逐项登记归类**（三审 H-2）：不能只凭"有三个接口"就声称覆盖。落地时产出一份调用点清单，每项标注走 strict / plain / rich 哪一条，作为第 4b 步的交付物之一。

**另产出「模板内字位展示来源清单」**（四审 M-8）：模板里还有不经过 `colorWord` 的字位展示——首页 hero 文案、品牌周标题、示例墙字面串、声音块、flash、打印小书路径、各处 ARIA。每一项逐条标记为**数据驱动 / 刻意静态文案 / 必须迁移**三者之一。只登记 42 个着色调用点覆盖不到这条。

**禁止用正则直接在整段 HTML 上分词**。单词场景仍走严格路径，分不出来就是数据错误，应该报。

四周现有数据的 `line` / `title` 实测**都不含标签**，但 `assessment_contract.js:2` 的 `tokens()` 里有 `replace(/<[^>]*>/g, ' ')`——系统是**预期文本可能带标签**的，所以边界必须现在定义，不能靠"当前数据碰巧没有"。要加尖括号、`&`、引号和允许标签的 fixture。

不能分的词原样输出（转义后），是"降级要换形态"的应用：句子里遇到不认识的词，换的是渲染方式，不是删掉着色能力。

## 6. 风险

- **week04 余量 0.38 MB**。首审 M-10 判 v0.1 的"不加媒体所以不会触线"证据不足：单文件构建会把公共 JS 复制进每个产物，新增解析器、错误文本和兼容分支都会进去，方案自己也承认 data.js 会增大。改为**低风险但必须测量**，每个接线提交记录增量。
