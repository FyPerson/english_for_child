## 第一层：非技术总结

codex 判定方案可以定稿，条件是修掉两条我自己修出来的矛盾。第一条：我在 v0.2 写"第 1 期完成后把周文件预算从 8 MB 降到 6 MB"，可第 1 期的核心承诺恰恰是"每个周文件的媒体字节一个都不变"，week04.html 现在就是 7.38 MB，正确实现必然被护栏判红。根因是我把"仓库里去重后 8.3 MB"误当成了"单周文件会变小"，单文件交付下每周仍带自己那份全量媒体，去重的收益只在仓库体积和合并入口。第二条：§3.8 说"三个素材工具都写 PROVENANCE"，同一节又说"PROVENANCE 只记 adopted 下的文件"，而两个音频工具写的是 assets 目录，实现者不知道该听哪句。四条 medium 都是契约最后的边角：同内容重跑时目标文件已存在怎么办、一个文件被多处引用时溯源记哪一次、音素清单是全量重建还是增量合并、Release 要不要附上 manifest.json 本身。修法都是唯一的，一并写进 v1.0。

## 第二层：4 件套

### H-1（high / contradiction）§3.3、§3.5、§4 第 1 期第 4 到 5 步、§5
> codex 原话：第 1 期要求四个周文件的骨架、声明顺序以及全部媒体字节与基线完全相等，清单化仍会把媒体重新内嵌进每个独立周文件，不会显著缩小周 HTML；预算却从 8 降到 6，现状表又记载第四周媒体 7.05 MB。正确实现很可能必然被 6 MB 护栏判失败。
> codex 建议：不要预先写死 week=6；或维持 8；明确 7.05 MB 的口径。

**建议：采纳，维持 8。** 我在写 v0.2 时把"仓库去重后 8.3 MB"当成了"单周会变小"。单文件交付的体量只由该周媒体决定，本方案的去重只作用在仓库与合并入口。
**不采纳理由**：可以按"第 1 期后取四周最大值加余量"动态定。但那等于把阈值交给实测，护栏就没有先验约束力了；8 MB 本来就是"别再涨"的线。
**🔟 第十人（基础假设）**：这条 high 存活了三轮没被抓到，说明我和 codex 前三轮都默认"清单化会让文件变小"。基础假设错了，写进 §3.3 推论与 §7 风险，防止下次再犯。采纳。

### H-2（high / contradiction）§3.1、§3.8、§4 第 1 期第 7 步
> codex 原话：第 7 步开头称三个工具都写 adopted、PROVENANCE 与 manifest，§3.8 也称三个工具统一在 adopted 的 staging 发布；随后又规定两个音频工具写 assets 既有目录，PROVENANCE 只记 adopted。实现者无法判断。
> codex 建议：分两类写契约：embed_assets 写 adopted、PROVENANCE、manifest；音频工具写 assets 与 manifest，不写 PROVENANCE；各在目标父目录 staging。

**建议：采纳。** 音素与词音目录本来就是"一键一文件"的真相源，按键命名、允许同键覆盖，与内容寻址是两套正确的模型，不该强行统一。
**不采纳理由**：可以把音频也搬进 adopted 走内容寻址。但 `resources/assets/phonemes/README.md` 已声明自己是真相源，副机的发音回炉流程也建立在按键命名上，改了要动交接规范。
**🔟 第十人（历史踩坑）**：《修订稿机械核对》：改一处其他章节没跟上。v0.4 §3.8 是新写的节，我没回头对第 7 步首句。采纳。

### M-3（medium / edge-case）§3.8 整批发布第 3 步
> codex 原话："rename 只会新增文件"没覆盖幂等重跑：相同 slug 相同内容得到同一目标名而目标已存在；不同平台 rename 行为不同；10 位前缀有极低碰撞概率。
> codex 建议：目标存在时先算完整 sha256 并核对 mime，相同则跳过复用，不同则整体失败绝不覆盖；两例测试；成功失败都清理 staging。

**建议：采纳。**
**不采纳理由**：找不到。
**🔟 第十人**：用 3 个角度检查后未发现实质反驳。采纳。

### M-4（medium / ambiguity）§3.8 同内容多键、PROVENANCE 字段
> codex 原话：同一媒体可被多键多周引用，但 PROVENANCE 每条只定义单数来源；没说只记首次还是记全部，工具后续引用是否改写。
> codex 建议：二选一固定；若首次来源，排序沿用周序声明序键序，并测试新增别名不改既有条目。

**建议：采纳，只记首次。** 引用关系在清单里已经完整，PROVENANCE 只回答"这个字节从哪来"，一次就够。
**不采纳理由**：记全部来源信息更全。但那让 PROVENANCE 变成第二份引用表，与 H-3（归档 32）"存活真相只有清单"相悖。
**🔟 第十人（心智成本）**：单一职责比信息全更省心智。采纳。

### M-5（medium / missing-constraint）§4 第 1 期第 7 步 build_phonemes
> codex 原话：没确定是全量重建还是合并现有清单；现工具向 HTML 累计合并；只按本次 src 重建会丢跨周复用的旧音素；默认合并则删源不删条目，与 --remove 语义要协调。
> codex 建议：读本周 SOUNDS 所需 audioKey，以 phonemes 目录为真相源全量重建；别名只引用实际音频键。

**建议：采纳，全量重建。** 实测四周 `PHONEME_AUDIO` 键集合恰等于 `SOUNDS` 所需集合，全量重建不会丢任何键；`k` 用 `audioKey:'c'` 这种别名由 SOUNDS 表达，清单里只出现实际音键。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：全量重建依赖"phonemes 目录始终齐全"，而它正是 README 声明的真相源；缺文件即失败是对的行为。采纳。

### M-6（medium / missing-constraint）§3.7、§5
> codex 原话：Release 按 manifest 文件键上传，manifest.json 自身不在 files 映射里，Release 不含它；本机 build 只生成五个 HTML，artifact 与本机构建"逐文件一致"覆盖不了 index.html 与 manifest.json。
> codex 建议：显式加入 manifest.json；验收分两层：五个 HTML 对 build，完整包对同提交 release/package。

**建议：采纳。** index.html 是 `package()` 里的常量字符串，manifest.json 由哈希决定，两者都可重现，七文件对 release 产物比对成立。
**不采纳理由**：找不到。
**🔟 第十人**：用 3 个角度检查后未发现实质反驳。采纳。

### L-7（low / readability）§3.3 基线命令测试
> codex 原话："不引用写入基线的函数"过度绑定实现结构，共享只读辅助函数也可能误报；真正风险是命令执行后 fixture 变化。
> codex 建议：行为测试：预置 baseline 记录字节，运行 build 与 check 后断言不变；另测无 --force 时拒绝。

**建议：采纳。**
**不采纳理由**：找不到。
**🔟 第十人（历史踩坑）**：《降级要换形态》：断言锁行为不锁实现。采纳。
