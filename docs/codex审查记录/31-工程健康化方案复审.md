## 第一层：非技术总结

上一轮的 14 条基本都落进去了，但这一轮 codex 抓到两条 critical，其中一条是我自己修出来的错：为了防止合并页的 JSON 里出现 `<!--` 截断脚本块，我写成把它转义成 `<\!--`，而 JSON 根本不允许这种反斜杠写法，浏览器一解析就失败，等于把合并入口修坏。另一条是历史清理的顺序：先删分支再枚举历史文件、清理规则用 `*.html` 通配会误伤设计文档和四个模板、filter-repo 跑完会把 origin 远端配置删掉。六条 high 都是"写了目标没写接口"：可重现构建要一个输出目录参数，现在没有；CI 说上传 manifest.json，但那个文件只有 release 打包才生成；清单没规定键的字符集与重复键处理；骨架哈希没说怎么切分；清单到底放哪一处两段话不一致；WALL_ILL 这一类插画没有任何工具会产出。核实时还多查出一件事：庆祝图 CELEBRATE_NAT 是单个字符串声明，不是键值对象，v0.2 的 schema 装不下它。

## 第二层：4 件套

### C-1（critical / security）§3.6、§4 第 0 期第 5 步
> codex 原话：`json.dumps` 后把 `<!--` 替换为 `<\!--` 会生成非法 JSON 转义，浏览器 `JSON.parse` 会失败，与验收要求直接矛盾。
> codex 建议：改用合法转义，例如把 `<` 编码为 `\u003c`，并增加直接调用 `JSON.parse` 的回归测试。

**建议：采纳。** 我在 v0.2 把 `</` → `<\/` 这条合法规则类推到了 `<!--`，类推错了。改成替换全部 `<` 更简单：JSON 语法本身没有 `<`，替换只会落在字符串里，一条规则同时覆盖 `</script`、`<!--`、`<script`。已用 Python 验证还原相等。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：这是《修订稿机械核对》记录的同款：修订引入的缝比原稿多。这一条在送审前只要写一个 `json.loads` 单行验证就能抓到，我没做。采纳，并把"转义规则必须附可执行验证"写进 §3.6。

### C-2（critical / security）§4 第 0 期第 7 步
> codex 原话：未核对所有远端 heads、tags；路径枚举安排在删 refs 之后；filter-repo 可能移除 origin 远端配置。
> codex 建议：删 refs 前保存并核对完整引用清单；先枚举再删；重写后重建并验证 origin，强推前再核对。

**建议：采纳。** 十个子步骤把顺序写死：快照 → 副机停工 → 固定清单 → bundle 恢复验证 → 删分支 → 重写 → 核对与重建 origin → gc → 强推 → 对照表。
**不采纳理由**：单人项目、引用只有 6 个，快照看似形式。但 G 是逆建议的决定，形式就是保护。
**🔟 第十人（时间维度）**：这些步骤只执行一次，写十步会不会过细？反过来想，正因为只执行一次，没有第二次机会纠错。采纳。

### H-3（high / contradiction）§4 第 0 期第 7 步"清除路径"
> codex 原话：`git log --all -- '*.html'` 会匹配 `docs/design/design-doc.html` 等文档 HTML，配合 `--invert-paths` 可能误删应保留的历史。
> codex 建议：只接受根目录产物名，单独列出，对文档 HTML 做保护性断言。

**建议：采纳。** 实测通配命中 13 个路径，其中四个模板是**源码**，误删它们等于删掉课件的全部历史。清单固定为七个名字。
**不采纳理由**：找不到。
**🔟 第十人（历史踩坑）**：《修复也是改动》：删旧东西前盘点范围。我在 v0.2 写了"列出全部产物名"却没有真的列，这一条 codex 替我列了。采纳。

### H-4（high / contradiction）§3.4、§4 第 0 期第 2 步、§5
> codex 原话：现有 `--check` 只读根目录，没有输出目录参数；先 build 再 check 变成自检，不能验证独立重建。
> codex 建议：定义 `build --output-dir <temp>`，两次构建分别写入并比较。

**建议：采纳。** `--output-dir` 二十行以内；原 `--check` 语义在新模型下没有对象，删除。
**不采纳理由**：可以两次都写根目录、中间存一份哈希。但那会让第二次构建覆盖第一次的产物，测试读到的是哪一份说不清。
**🔟 第十人**：用 3 个角度检查后未发现实质反驳。采纳。

### H-5（high / missing-constraint）§3.7、§5
> codex 原话：check job 计划上传根目录 manifest.json，但它只在 `dist/<版本>/` 生成；artifact 名称、`if-no-files-found`、下载与 Release 创建动作都没定。
> codex 建议：明确 artifact 路径与唯一名称，缺文件必须失败，release job 下载后用固定 action 创建 Release 并验证字节一致。

**建议：采纳。** check job 直接跑 `project.py release`：它本来就是 build + 完整回归 + 打包，产物目录自带 manifest.json，正好是要上传的东西。
**不采纳理由**：release 会跑完整浏览器回归，CI 时长比 check 略长。但 CI 现在跑的 check 也是完整回归，没有额外成本。
**🔟 第十人（成本价值）**：第一年可能只打几次 tag，release job 会不会白写？artifact 每次 push 都有，Release 只是给稳定链接；两个 job 加起来不到 30 行。采纳。

### H-6（high / missing-constraint）§3.2
> codex 原话：固定单引号格式没约束键字符集；重复 JSON 键会被静默覆盖；未知顶层键未规定。
> codex 建议：限制键为明确字符集或规定转义；用拒绝重复键的解析；拒绝未知顶层键与字段。

**建议：采纳。** 实测 652 个键全部匹配 `^[A-Za-z0-9 ,.!?-]+$`，直接写死这个正则，不做转义逻辑。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：会不会以后出现带撇号的句子键，比如 `Nat's`？那时改正则并同步生成器的转义，是一次明确的决定，比现在预留转义逻辑更可控。采纳。
