## 第二层：4 件套

### M-1（medium）候选过滤对非对象条目抛原生错误
> codex 原话：未使用 `--include-candidates` 时，代码直接对每个条目调用 `v.get(...)`；条目若是数组、字符串或 null，会在进入 `validate()` 前抛 AttributeError，破坏"类型模糊一律拒绝"的失败关闭语义。
> codex 建议：过滤前先检查 `isinstance(v, dict)`，或先统一执行条目结构校验再决定是否跳过候选。

**建议：采纳。** 一行条件；不改则 docstring 里"类型模糊一律拒绝"的声明有一条路径不成立（能力声明大于实作）。
**不采纳理由**：条目不是对象是极端误配置，traceback 也能定位。
**🔟 第十人（基础假设）**：无实质反驳；确认采纳。

### M-2（medium）键与 sound_id 拼路径无限制
> codex 原话：`source.sound_id` 未限制类型或内容并直接拼入缓存路径，顶层键也直接拼入 `<key>.wav`；`../` 或 Windows 反斜杠可能写到预期目录之外，甚至覆盖已有文件。
> codex 建议：`sound_id` 为正整数并拒绝路径分隔符；spec 键验证为安全的 basename（本项目可限制为单个小写字母），或 `Path(key).name == key`。

**建议：采纳（键限制放宽到 `^[a-z]\w*$` 而非单个字母）。** SOUNDS 键将来可能是双字母（如第五周的 `sh`、`ck`），单字母限制会在那时挡路；`\w` 已排除路径分隔符。`sound_id` 在 Freesound 就是正整数，直接按正整数校验。
**不采纳理由**：spec 由 Claude 维护、只在本机跑，"恶意 key"不存在；这是把单人脚本当对外服务防。
**🔟 第十人（成本 / 价值）**：价值主要是"误填"而不是"恶意"——副机 GPT 将来按清单复跑时，一个 `sound_id: "193279/"` 的手误就会写出目录外；6 行校验换一个不会静默出错的复跑路径。确认采纳。

### L-1（low）source 文字字段可为空
> codex 原话：`preview / sound_id / author / title / license` 仍可为 null、数组或空字符串，错误会延迟到 URL 请求、路径格式化或日志阶段才以 TypeError / 网络错误暴露。
> codex 建议：为 URL、作者、标题、许可字段增加非空字符串校验；`sound_id` 正整数校验；下载前报告带键名的配置错误。

**建议：采纳。** 与 M-2 同一处代码、同一次改动。
**不采纳理由**：找不到实质反向理由。
**🔟 第十人**：用 3 个角度检查后未发现实质反驳，确认采纳。
