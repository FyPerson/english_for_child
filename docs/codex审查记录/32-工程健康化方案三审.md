## 第一层：非技术总结

critical 清零，上一轮的 JSON 转义、构建输出目录、清单标量形态、历史清理路径都被判"实质收紧"。这一轮的六条 high 集中在两件事上。第一件是"数据一致性契约还差最后一层"：adopted 目录里的文件名直接用业务键，键允许问号和空格，Windows 会拒绝；PROVENANCE 与清单谁是存活真相没说清，孤儿文件永远清不掉；素材工具的"先写 .tmp 再改名"只保证单文件原子，一批文件处理到一半失败会留下"清单没变但文件字节变了"。第二件是"步骤顺序"：历史重写在强推之后才更新仓库内的对照文件，等于推完立刻又分叉；基线由普通 build 生成会让基准跟着被测对象漂移；release job 只写了 tag 触发没写 job 级条件。核实后我把前一件事合成一个新章节 §3.8：文件名带内容哈希后缀，被清单引用的文件从构造上就不可能被覆盖，一条规则同时回答了命名、覆盖、回滚三条 high。

## 第二层：4 件套

### H-1（high / contradiction）§4 第 0 期第 7 步子步骤 9 到 10、§5
> codex 原话：子步骤 9 先强推并核对远端，子步骤 10 才把 commit-map 写入对照文件并更新含旧提交号的文件；若这些文件在仓库内，步骤 10 会产生未提交的修改，"远端已完成重写"的核对立即失效。
> codex 建议：filter-repo → 生成并核对映射 → 更新文件 → 提交 → 最后一次 force push → 核对同点。

**建议：采纳。** 归档与项目记忆都在仓库内，这条顺序错误会让副机 clone 到一个缺对照表的版本。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：我在 v0.3 默认"对照表是事后文档"，其实它是重写后 main 的一部分。采纳。

### H-2（high / edge-case）§4 第 1 期第 1 步、§3.2 第 3 条、§3.1
> codex 原话：canonical 文件名取业务键，但合法键允许空格、逗号、句点、感叹号和问号，问号在 Windows 非法，句点或空格结尾也不安全。
> codex 建议：确定性跨平台编码，例如安全短前缀加内容哈希，或仅 `[A-Za-z0-9_-]`；明确大小写碰撞、保留名、尾随点/空格、路径长度。

**建议：采纳，取内容寻址。** 实测当前无源键全部安全，但"当前安全"不是规则。内容哈希后缀还额外买到一个性质：被引用文件不可能被覆盖，H-4 的整批原子问题一半靠它解决。
**不采纳理由**：可以只限制 slug 字符集、不加哈希，文件名更好读。但那样"改图重生成"会覆盖同名文件，H-4 就要靠更复杂的回滚逻辑。
**🔟 第十人（心智成本）**：副机看到 `snake-3fa9c2b1e0.png` 会不会困惑？清单里键仍是 `snake`，副机只跟键打交道，文件名由工具生成。采纳。

### H-3（high / contradiction）§3.1 PROVENANCE、§4 第 1 期第 1 与第 7 步、§5
> codex 原话："覆盖 adopted 下每个文件"按字面含 README 与自身；`--prune` 只删"PROVENANCE 与清单都不引用"的文件，而初次导出要求 PROVENANCE 覆盖全部媒体，孤儿永远被旧 provenance 引用无法回收；素材工具没规定同步更新 provenance。
> codex 建议：PROVENANCE 只记媒体；四周 manifest 为存活真相；prune 同步移除条目；工具原子更新 provenance。

**建议：采纳。** 存活真相只能有一个，就是四周清单；PROVENANCE 是溯源记录不是引用。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：这是"两个真相源"反模式的又一次出现，与 capture 回写同款。采纳。

### H-4（high / missing-constraint）§4 第 1 期第 7 步
> codex 原话：单文件 .tmp 改名只保证单文件原子；前几个文件已替换、后续失败，旧 manifest 仍可能指向已被覆盖的新字节；prune 不能恢复被覆盖文件。
> codex 建议：整批 staging，已引用目标哈希不同则提交前失败，再按受控顺序发布；至少保证失败不改变任何已引用文件的字节。

**建议：采纳。** §3.8 五步：staging → 校验 → rename 新增 → PROVENANCE → 清单。内容寻址之后 rename 只会新增文件，"覆盖已引用文件"在构造上不可能发生，剩余风险只是留下未引用的新文件，由 prune 回收。
**不采纳理由**：找不到。
**🔟 第十人（历史踩坑）**：《修复也是改动》三层设防的思路：回调 / 状态 / 物理。这里物理层是内容寻址，状态层是清单最后写，流程层是 staging。采纳。

### H-5（high / ambiguity）§3.3、§4 第 0 期第 1 步
> codex 原话：基线"由 build 生成"，若普通 build 每次都更新入库基线，基准随被测输出漂移；若不会，第 0 期第 1 步缺少创建入口。
> codex 建议：独立一次性命令，要求工作区干净、fixture 不存在或显式覆盖，记录 HEAD；build/check 只读。

**建议：采纳。** `project.py baseline --create`，并加一条单元测试断言 build 与 check 不引用写基线的函数。
**不采纳理由**：找不到。
**🔟 第十人（基础假设）**：我把"基线怎么算"写清了，没写"谁在什么时候算"。采纳。

### H-6（high / missing-constraint）§3.7
> codex 原话：release job 只写了 tag push 触发，没有 job 级 `if`；顶层触发含所有 push 与 PR，照表拆 job 会在普通 push 上执行 `gh release create`；下载目录与文件展开未固定。
> codex 建议：`if: startsWith(github.ref, 'refs/tags/v')`；固定 download path；断言恰好一个目录；校验 manifest；明确文件列表。

**建议：采纳。**
**不采纳理由**：可以把 release 拆成独立 workflow 只监听 tag。但那样 artifact 不在同一 run 内，"同一批字节"要靠再次构建保证，正是 H-5 上轮要避免的。
**🔟 第十人**：用 3 个角度检查后未发现实质反驳。采纳。

### M-7（medium / contradiction）§4 第 0 期第 7 步子步骤 7 与 9
> codex 原话：`for-each-ref` 只剩 main 在 fetch 后不成立；`ls-remote` 输出含符号 HEAD，按字面永远失败。
> codex 建议：精确 ref 集合；远端断言 heads 仅 main、tags 为空、单独允许 HEAD。

**建议：采纳。** 实测 `git ls-remote origin` 确实带 HEAD。
**不采纳理由**：找不到。
**🔟 第十人（历史踩坑）**：《降级要换形态》：断言别锁瞬时状态。"只剩 main"就是瞬时状态，精确集合才是可复验的。采纳。
