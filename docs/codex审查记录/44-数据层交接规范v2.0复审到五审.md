### 一条反驳（四审确认成立）

三审 medium 称 `assessment_contract.js` 依赖**虚构**的 `output` 块类型，建议删除该依赖。核实后不成立：`output` 是真实且在用的块。四审原话确认：「对'删除虚构 output 依赖'的反驳成立：所给 render-blocks.js 确实存在 `output` 分支，原三审对其称谓不准确；第四稿把真实问题改述为类别映射不完整是正确方向。」

由此顺出一次全量对齐：把 `render-blocks.js` 的 24 个 `case` 与规范表、四周数据实际用到的块三方比对，发现规范表**漏了 6 个在用的块**（`initialpick`/`retest`/`probe`/`output`/`assessment`/`baseline`），而表头一直写着"只能用这些，不能发明新的"。这次是主动找到的，不是等 codex 逐个指。

## 沉淀

- **「能力声明 ≠ 实作」在同一份文档里犯了两次**：首审 critical 1（把未实现的校验写成"校验器会查的"）、复审 M1（写"三条已移进 §4.1"而表里没有）。第二次发生在我刚把第一次写进归档沉淀之后。处理办法已落地为 `tools/check_doc_claims.py`——它在第二稿上独立复现了 codex 判 M1 未修的那三条。
- **更根本的一类错误：为一个自己没读过的东西写规范。** `reread` 结构、`W` 的累计语义、`audioKey` 与上墙的关系，三次都是只读了 `META` 就设计 schema，没读实际数据。`check_doc_claims.py` 兜不住这类——它只验声明有没有落点，验不了 schema 符不符合真实数据。**改 schema 前必须先读该结构的真实实例**，这条要进项目记忆。
- **送审 brief 列基础假设逐条证伪，首次实施即见效**：首审 8 条假设判出 3 条不成立，其中"双字母延后不阻塞 W6"直接否定了我给用户的排期建议。这一法应固化进后续所有方案类送审。
- **验证工具本身也要验证**：调 `check_doc_claims.py` 时，我先用错误的路径测反例（MSYS 的 `/tmp` 与 Windows Python 的 `/tmp` 不是同一目录），又在乱码输出里 `grep -c "行"` 统计条数，两次都得到"通过"的假象。差一点把一个没验证过的工具的绿色结论当成证据。
