### 2.3 `rack` 是多重集，不是集合

四周实际值：

| 周 | `wallLetters` | `rackG4` | `rackG5` |
|---|---|---|---|
| W1 | `satipn` | **`ssaattiippnn`**（每字母两块，12 块） | 同左 |
| W2 | `ckehrmd` | `atpncehmrd`（10 块） | `satipnckehrmd` |
| W3 | `goulfb` | `aouhmdglfb`（10 块） | `satipnckehrmdgoulfb` |
| W4 | `satipnckehrmdgoulfb` | `satipnckehrmdgoulfb` | 同左 |

**第一周每个字母有两块积木**，因为它要摆 `nn`、`pp` 这类。迁移成数组时**必须保留重复项**——用 `Set` 或去重会让第一周的 G4/G5 直接摆不出词。

### 2.4 基线比对四项

`baseline.py:46` 与 `:140`：`sha256`、`skeletonSha256`、`declarationOrder`、`media`。改 `META` 会改变 data.js 内容，进而改变构建产物，**前两项必变**，所以基线必须在改造完成后重取。

## 3. 设计决策

### 3.1 分词函数放哪

新建 `frontend/src/shared/graphemes.js`，导出两个函数：

```js
tokenize(word, patterns)   // 按已教字位集合最长匹配，返回字位 ID 数组
graphemesOf(word, SOUNDS)  // 上一个的便利包装，从 SOUNDS 取字位表
```

放 `shared/` 而不是各游戏内部，因为 §2.2 的 13 处要共用同一份实现——各写各的必然漂移。模板通过 `@include shared/graphemes.js` 引入，与 `games.js`、`state.js` 同级。

### 3.2 三个字段的数组形态

```js
wallLetters: ['s','a','t','i','p','n']          // 有序，顺序即点亮顺序
rackG4: ['s','s','a','a','t','t','i','i','p','p','n','n']   // 保留重复，长度即块数
rackG5: [...]                                    // 同上
newPatterns: ['ai','j']
```

**保留重复是硬要求**（§2.3）。`canSpell` 的逐个消耗语义不变，只是消耗单位从字符变成字位 ID。

### 3.3 同形多音的 schema：现在定，不实现

`oo_short`/`oo_long`、`th_unvoiced`/`th_voiced` 要到 W13、W16 才用。**本次只在 `SOUNDS` 的键上留出空间**（键即字位 ID，与 `grapheme` 分离），不写消歧逻辑、不加 `segments` 字段。

理由：键结构现在不动，将来就是第二次破坏性变更；而消歧逻辑没有数据可验，现在写等于写死一个没跑过的分支。规范 v2.0 §3 已写明"多解而 `segments` 缺失时校验器必须失败"——那条留到 W13 前实现。

### 3.4 分组判定改走 `SOUNDS.type`

`groupedRackHTML`（`games.js:583`）现在用 `vowels.includes(ch)` 判元音，`ch` 是单字符。改成字位后 `vowels.includes('ai')` 必然失配，`ai` 会被错分进辅音组。

**改用 `SOUNDS[字位ID].type === 'v'`**——这个字段 schema 里本来就有（规范 v2.0 §3：`'c'` 辅音 / `'v'` 元音），第三周实测 14 辅音 + 5 元音齐全，不需要新增数据。

里程碑 0 的分组方案本身**在字位粒度下仍然成立**：该函数的注释写明「tiles 的索引仍是 `RACK_LETTERS` 的索引，G4 / G5 的入槽逻辑不受影响」，索引语义与元素类型无关，改成数组后不变。

### 3.5 迁移必须一次做完

`rackG4` 从字符串改数组，四周数据必须**同时**改，否则 `build` 当场失败——没有"先改引擎再逐周迁移"的中间态。所以第 3 步是一个不可分割的大 commit。

## 4. 分步实施

每步结束时仓库必须可构建、`check --quick` 全绿。每步一个 commit，逐步送审。

| 步 | 内容 | 验收 |
|---|---|---|
| **1** | 新增 `shared/graphemes.js` 与单元测试。**不接线**，纯新增 | `check --quick` 全绿；新测试覆盖：单字母词、双字母词、最长匹配优先、未知字位报错 |
| **2** | 校验器改造：`check_data.js` 6 处 + `assessment_contract.js:48` + `load_data.js:24` 改用分词函数。**此时数据仍是字符串**，分词函数对单字母输入行为等价 | `check_data.js` 对四周现有数据输出与改造前**逐字节相同**（这是关键回归） |
| **3** | **迁移**（不可分割）：四周 data.js 的三个字段改数组 + 引擎 §2.2 的 #1–#9 + 四个模板的 #10 | `build` 六个 BUILT 失败 0；`check --quick` 除基线外全绿 |
| **4** | 基线重取：`baseline --create --force` | `check` 全绿（含浏览器回归） |
| **5** | 双字母冒烟：造一个含 `ai` 的测试周 fixture，验 G2 拆 3 块、G4/G5 能摆、点亮墙显示 1 块 | 新测试通过；四周现有测试不受影响 |

**第 2 步是整个方案的安全垫**：它让分词函数在真实数据上跑一遍，但输出必须与旧逻辑完全一致。这一步过了，才有信心做第 3 步的破坏性迁移。

## 6. 风险

- **week04 余量 0.38 MB**。本次改造不加媒体，理论上不影响体量；但 `rackG4` 从 19 字符变成 19 元素数组会让 data.js 变大几百字节，构建产物随之微增。第 3 步后要立刻看 `size budget` 输出。
- **第 3 步不可分割**，一旦中途出错，回滚范围是整个 commit。做之前先 `git rev-parse HEAD` 记基线。
- ~~里程碑 0 的分组固定位是否仍成立~~ **已核实，见 §3.4**：分组方案不受影响，只需把元音判定从 `vowels.includes(ch)` 换成 `SOUNDS[id].type === 'v'`。
- **审查轮次不可控**。2026-09-08 两份纯文档分别走了五轮和六轮；代码改动的审通常更细。若走到五轮，本方案的 4 天估算要加 1–2 天。
