# handoff（全局跨项目）

把当前项目整理成**接手方（换机器的你自己 / GPT / 同事 / 另一个 Claude）不用回读会话历史就能继续干**的状态，然后推到 GitHub。

核心判断：**过期的交接信息比没有交接信息更糟**。接手方拿到"分支未合并、某功能未提交"这类陈旧断言，会照着它做出错误决定。所以本 SKILL 的重心不在"写文档"，在**逐条核对事实**。

## 非目标

- **不做灾备备份** → 那是 `/backup-memory`（镜像到 `E:/_backups/`，防硬盘挂）。本 SKILL 是把知识**转换**进仓库，两回事。
- **不写 Claude 记忆** → 那是 `/remember`。本 SKILL 只**读**记忆并转换，方向相反。
- **不重造文档落位校验** → 调 `/tidy-docs` 收尾模式，不复制它的五项校验。
- **不自动触发**。只在用户显式 `/handoff` 时跑。
- **不自动改远端**。任何 push（尤其 force-push）都要用户拍板。
- **不做回流**（接手方改完再回到 Claude）。v1.0 只管单向。真碰上了再设计，别凭空想。

## 模式

| 调用 | 模式 | 侧重 |
|---|---|---|
| `/handoff` | **换机检查点**（默认） | 「当前状态快照 + 下一步干什么 + 别丢未提交的」。可反复跑 |
| `/handoff final` | 终局交接 | 多一层完整性审查：许可/署名、密钥扫描、依赖可重建、无本机绝对路径 |
| `/handoff <路径>` | 局部 | 只处理指定子目录（少用） |

## 第 0 步 · 自适应探测（每次必做）

全局 SKILL 不能假设项目结构。**先探测再决定跑哪些步**：

```bash
ROOT="$PWD"
git -C "$ROOT" rev-parse --is-inside-work-tree >/dev/null 2>&1 || echo "非 git 仓库"
git -C "$ROOT" remote -v                      # 有无 remote
gh auth status 2>&1 | head -5                 # gh 是否登录
git -C "$ROOT" branch --show-current          # 当前分支
# 项目记忆位置（Claude Code 的 auto-memory 在仓库外）
ls "$HOME/.claude/projects/"                  # 找与本项目对应的 slug 目录
# 文档目录：沿用 tidy-docs 的探测（docs/local > docs > 根 .md）
```

**探测结果 → 步骤启停**：

| 探测 | 影响 |
|---|---|
| 非 git 仓库 | 停下来问用户是否 `git init`，不擅自建 |
| 无 remote | 第 7 步要先建/挂 remote，先问用户仓库地址或是否用 `gh repo create` |
| 无项目记忆目录 | 第 5 步降级：只做第 6 步的接手入口，不做记忆转换 |
| 无文档目录 | 第 4 步跳过，接手入口放仓库根 `README.md` |
| **远端仓库是 PUBLIC** | ⚠️ 第 7 步前必须提醒（见硬规矩 5） |

**抛探测确认块**给用户：

> 📍 **handoff 范围**
> - 项目 / 文档目录 / 记忆目录
> - 远端仓库 + **可见性**
> - 分支：当前 vs 默认，领先/落后几个 commit
> - 本次跑：<哪几步；哪几步跳过 + 原因>

## 七步

### 第 1 步 · 盘点未提交工作

```bash
git status --short --untracked-files=all
git stash list
```

**必须区分两类**，这是最容易漏的地方：

- **本次会话的改动** —— 你有上下文，不会漏
- **会话之前就压在工作区的改动** —— ⚠️ 最危险。它们看起来像背景噪音，实际可能是一整段从未提交的产出

> **实证**：2026-09-01 这个项目 handoff 时，工作区压着一段从未提交的工具链（4 个新工具 + 交接文档共 1264 行）和一批课件功能改动。若只提交"本次会话改的"，那两段直接丢在旧电脑上。

逐个未跟踪文件问一句：**这是产出物，还是临时垃圾？** 垃圾进 `.gitignore`，不要混进提交。会话锁、pid 文件、本地 settings 一律不该被跟踪。

### 第 2 步 · 逐条核对事实 ⭐ 最关键

从**记忆文件 + 现有文档 + 你打算写进交接文档的每句话**里，抽出所有**状态断言**：

> 「X 已完成」「Y 尚未提交」「分支在 Z 未合并」「某某缺 N 个」「某流程跑不通」

每一条都拿去和**磁盘 / git / 实跑**比对，输出两栏：

| 断言 | 记忆写的 | 实际 | 处置 |
|---|---|---|---|
| … | 未提交 | 已提交于 `abc1234` | 更正 |
| … | 素材全缺 | `find` 确认仍 0 个 | 保留 |

核对手段按可靠性排序：**实跑 > 读文件 > 读 git > 凭印象**。能跑就跑一遍，别只对比常量值就下结论（见硬规矩 2）。

**这一步不通过，不许进入第 5 步。**

### 第 3 步 · 分组提交

按**性质**分组，不按时间顺序，也不要一坨提交。

**大 diff 必须看完**（见硬规矩 3）。二进制/base64/压缩产物先折叠再看结构性差异：

```bash
diff <(sed 's#data:[a-z/]*;base64,[A-Za-z0-9+/=]*#<B64>#g' 旧) \
     <(sed 's#data:[a-z/]*;base64,[A-Za-z0-9+/=]*#<B64>#g' 新)
```

commit message 写**实际包含什么**，不写"我以为它是什么"。一个 commit 同时含功能改动和素材更新，就两样都写。

需要把同一文件的改动拆进不同 commit 时：备份工作区版本 → 造出只含该部分改动的版本 → `git add` → 恢复工作区 → 提交。**注意**：之后任何 `git add -A <目录>` 都会覆盖这个精心构造的索引，拆分要放在该目录最后一次 `add` 之后。

### 第 4 步 · 文档落位

调 `/tidy-docs` 收尾模式，传入本次新建/移动/改名的文档清单。不重复实现它的校验。

### 第 5 步 · 记忆转换入库

把 Claude 会话记忆（`~/.claude/projects/<slug>/memory/`，在仓库外、换机器不跟着走）转成仓库内文档。放 `<文档目录>/项目记忆/` 或项目已有的等价位置。

**转换不是搬运，四项改写缺一不可**：

| 改写 | 为什么 |
|---|---|
| `[[wikilink]]` → 真实相对链接 | 外部模型解析不了 wikilink，交叉引用会全断 |
| 去工具专用元数据（`node_type` / `originSessionId` / `modified`）→ 换成项目 frontmatter | 噪音，且与项目文档体例不一致 |
| 裸文件名 / 简写路径 → 仓库全路径 | `check_data.js` 对接手方没用，`tools/week-checks/check_data.js` 才有 |
| **用第 2 步的结果更正过期事实** | 核心价值所在 |

改完**逐个 `test -e` 验证链接**（中文路径用 shell `test -e`，禁用 Python `os.path.exists`——在 Git Bash 下对中文路径误判）。

**原记忆留在原地**，在其索引顶部加一条指针：权威版本已移入仓库某路径，本地这份是本机工作记忆、事实以仓库版为准。避免以后两份打架。

### 第 6 步 · 生成接手入口

写在记忆目录的 `README.md`（或仓库根 README，看项目结构）。骨架：

```markdown
## 0. 这个项目是什么      —— 一段话 + 产出形态 + 关键文件表
## 1. 现在到哪一步        —— 各阶段状态 + git 现状 + ⭐**唯一的下一步**
## 2. 从哪里开始读        —— 按「现在要用的 / 以后再读的 / 随时可查的」分档
## 3. 环境依赖            —— 表格：用途 → 依赖
## 4. 当前阻塞与未决项    —— 按优先级编号，每条写清「卡在哪、怎么解、谁能拍板」
## 5. 本目录导航
```

**必须有且只有一个「下一步」，并且写明「不是什么」**：

> ### 唯一的下一步：<一件事>
> **不是** <接手方最可能误选的那件事>。<两句话说清为什么>

> **实证**：接手方读完 README 后反馈「不确定该先补第二周素材，还是直接开始第三周」。
> 原因是文档同时给了两个信号——导航里把「周课件生产线／第三周怎么开工」标成 ⭐当前主线，
> 阻塞项里又把「补第二周素材」排在第 1 位。**两个都像"下一步"，接手方就得自己猜。**

**阅读顺序本身也在传递优先级**，别让它和「下一步」打架。把设计规范、下一阶段的契约
文档排在最前面，等于在说"先做下一阶段"。正确做法是分档：

- **A 档 · 现在就要做的** —— 只列完成「唯一的下一步」真正需要的几份
- **B 档 · 做到下一阶段再读** —— 现在读了也用不上，先别啃
- **C 档 · 随时可查的背景** —— 方法论、历史交接

同理，导航表里的 ⭐ 之类标记要写清它标的是**"方法主文档"还是"当前该做的事"**，
这两者经常不是同一个。

**环境依赖从脚本实际 `import` 反推，不靠记忆**：

```bash
grep -hE "^\s*(import|from) " <脚本> | grep -vE "标准库白名单"
```

**未决项要区分"技术判断"和"业务/教学判断"**。后者标明**不许接手方自己定**——它没有做这个判断的信息。

### 同时产出一份「换机验证清单」

接手方到了新环境**看不到这边的会话**，所以验证步骤必须随仓库走，写成
`<记忆目录>/换机验证清单.md`。五关，从客观验到主观：

1. 仓库拉全了吗 —— 自验证（`git status -sb` + `git fsck`），不比对写死的值
2. **产物还能用吗** —— 最重要，直接验"用户手上的东西还能不能用"
3. 环境依赖装起来 —— 逐条给验证命令
4. 工具跑得通吗 —— 含幂等性实跑
5. **交接文档够用吗** —— 只读 README、不看会话历史，能否答出「下一步干什么 / 卡在哪 / 先读哪个」

第 5 关是真正的验收。**要写明：答不上来的地方就地补进 README** ——那说明这边漏写了。

清单里要显式列出**「看起来像故障、其实是正确行为」**的已知项，否则接手方会当 bug 去查。

### 第 7 步 · 推送与校验

1. 分支策略问用户（默认分支能否快进？两个分支都推？）
2. **公开性确认**（见硬规矩 5）
3. push
4. **校验一致性**——不靠"push 没报错"推断：

```bash
git fetch -q origin
for b in <分支列表>; do
  [ "$(git rev-parse $b)" = "$(git rev-parse origin/$b)" ] && echo "✓ $b 一致" || echo "✗ $b 不一致"
done
```

5. 输出**交接一句话** + **精选包清单**（见下）

## 五条硬规矩

### 1. 事实核对不过，不许推

宁可交接文档里没有某条信息，也不能有过期信息。接手方会照着陈旧断言做决定。

### 2. 区分「产物」和「工具」

报告任何"坏了"之前，先问：**这影响的是用户手上正在用的东西，还是重跑流程的能力？**

> **实证**：本项目 handoff 时我断言"第一周音频管线跑不过"，把它列为头号阻塞。实际是：课件里 56 条音频完好、用户日常使用毫无问题；只有**重跑注入工具**时计数自检会拦（而且那正是自检该做的事）。我只对比了常量值就下结论，没实跑、没区分产物与工具。用户一句"我试用起来没遇到问题"直接证伪。

推论：**别人的自检/护栏报警 ≠ 产品坏了**。护栏拦住你，往往说明它在正常工作。

### 3. 大 diff 必须看完

> **实证**：同一次 handoff 里，我只看了某个 2.6MB diff 的前 60 行就把 commit 描述成"插画重灌"，实际它还含游戏题库扩容、分流逻辑改写、朗读倍率调整等一批功能改动。错误描述已推上 GitHub，后来只能重写历史修正。

折叠掉 base64 / minified / 二进制再看，看**全量**，不要 `head -N`。

### 4. 不要写「会自我失效」的事实

交接文档里区分两类值：

| 类型 | 例子 | 怎么写 |
|---|---|---|
| **固定历史锚点** | 「改造前基线是 `7f3eb85`」「第二周提交于 `28ed4a8`」 | 可以写死，它指的是不变的历史事实 |
| **当前状态值** | 当前 HEAD 的 SHA、「其后 N 个 commit」、当前文件哈希表 | **不许写死**，给出查询命令 |

> **实证**：README 里写「`main` 与 `v3-p0` 都在 `632d30c`」，写完之后又提交了四次，
> 接手方在新机器上第一时间就发现它过期了。改成 `632d30c → 77aade8` 没用——下次提交又坏。
> 正确做法是换成「两个分支保持同点，当前位置用 `git log --oneline -1` 看」。

同理，验证清单里「最新 commit 应等于 X」也是错的设计。正确判据是**自验证**：

```bash
git status -sb          # 与 origin 同点 + 工作区干净
git fsck --no-dangling  # 对象完整性
```

git 的内容寻址已经密码学地保证了一致性，比对文档里写死的哈希表反而更弱。
**凡是能由命令当场算出真相的，就别把答案抄进文档。**

### 5. 公开仓库要显式提醒

推送前如果远端是 PUBLIC，且仓库含**真人录音、照片、儿童相关内容、家庭信息、内部资料**中任何一项，必须显式提醒并等用户确认。理由要说清：公开内容可能被搜索引擎和爬虫缓存，**事后转私有也收不回**。

用户明确选择公开就照做，不反复劝。

## 精选交接包（两层交接）

仓库是**真相源**（完整、可克隆）。但直接把整个仓库丢给外部模型，它往往会去改不该改的文件。所以额外输出一份**本次任务精选包清单**：

> 📦 **这次只需要给接手方这几个文件**
> - `<契约/交接文档>` —— 说清要做什么
> - `<范例文件>` —— 照着改比照着规范凭空写准得多
> - 合计约 N KB
>
> **不要给**：`<完整产物文件>` —— 给了它大概率直接去改这个，而它无法在自己的环境里验证

清单内容按项目实际情况生成，上面是形状不是模板。判断依据：**接手方在它自己的环境里能验证什么**。它跑不了的东西，给了只会让它盲改。

## 交付清单

跑完 `/handoff` 应当满足：

- [ ] `git status` 干净，无遗漏的未跟踪产出物
- [ ] 每条状态断言都经实测核对，过期的已更正
- [ ] commit 分组合理，message 描述的是实际内容
- [ ] 文档落位通过 `/tidy-docs`
- [ ] 记忆已转换入库，链接逐个 `test -e` 通过
- [ ] 原记忆索引已加"以仓库版为准"指针
- [ ] 接手入口 README 含：是什么 / 到哪步 / 读什么 / 依赖 / 阻塞项
- [ ] **「唯一的下一步」明确写出，且阅读顺序与之一致**（不能一个说先做 A、一个暗示先做 B）
- [ ] 文档里没有「N 份专题」这类会随文件增减而失准的计数
- [ ] 环境依赖从实际 import 反推得出
- [ ] 本地与远端 SHA 逐分支比对一致
- [ ] 已产出换机验证清单，含「像故障其实正常」的已知项
- [ ] 文档里没有会自我失效的值（当前 HEAD / commit 计数 / 易变哈希）
- [ ] 工具无硬编码绝对路径（接手方可能在别的盘符或系统）
- [ ] 已输出交接一句话 + 精选包清单

## 约束

- 只在显式 `/handoff` 时跑
- 提交、推送、`.gitignore` 改动前都要用户确认
- **force-push 必须用户拍板**；改写已推送的历史前先建备份分支，并比对树哈希证明内容未变
- 中文路径一律用 shell `test -e`，禁用 Python `os.path.exists`
- 不擅自删除文件；清理类操作先盘点引用再问
